# Контролируемый поиск с проверкой доказательств

Инструкция для оператора и разработчика. Новый контур включается отдельно от
прежнего: по умолчанию `RAG_CORRECTIVE_PIPELINE=off`. Наличие кода, успешные
unit-тесты и высокий source recall не означают, что смысловое качество достигло
9/10. Перед общим включением нужны сравнение на одинаковом корпусе и ручная
проверка ответов по замечаниям тестеров.

Дополнительные эксперименты `RAG_SOURCE_READING=off` и
`RAG_TASK_SCOPE_CHECK=off` включаются независимо, только внутри этого контура.
Первый делает отдельную выборку точных исходных абзацев перед ответом; второй
добавляет оценку соблюдения исключённых пользователем тем в уже существующую
проверку ответа. Ни один из них не является доказательством смысловой точности.
Протокол, бюджеты, отказоустойчивость и границы диагностики описаны в
[SOURCE_READING_EVALUATION.md](SOURCE_READING_EVALUATION.md).

## Эксперимент: чтение кандидатов до потери контекста

`RAG_PREPACK_SOURCE_READING=off` — отдельный, пока выключенный по умолчанию
эксперимент внутри `RAG_CORRECTIVE_PIPELINE=on`. Сам по себе этот флаг не
переключает legacy-путь и не доказывает качество. Production env в рамках
разработки не меняется. Перед включением на общем стенде нужен quality gate.

При `on` существующий reader переносится с этапа после packing на первый
непустой пул кандидатов. Retrieval возвращает уже отфильтрованные по USER scope,
ACL, исключениям и редакциям кандидаты без преждевременного финального `top_k`.
Вход reader всё равно ограничен: `assign_evidence` допускает до двух бюджетов
конечного контекста, а reader проверяет собственный лимит 96000 символов и
отказывает атомарно, не обрезая условия или формулы. Эти лимиты не доказывают,
что весь пул поместится в token context конкретной модели; это проверяется
отдельно в runtime. Фильтры доступа не выводятся из сгенерированных запросов.

Reader выбирает существующие passage IDs. Перед применением программа повторно
проверяет весь snapshot, исходную задачу, план и дословные цитаты. Native packer
использует их только как приоритет: совпасть должны E-ID, файл, точный раздел,
все переданные идентификаторы редакции и исходная цитата. Подсказка не создаёт
доказательств и не отменяет приоритет непокрытых typed subjects, условий,
исключений и атомарных перечней/семейств. Coverage проверяется после packing.

При сборке нескольких кандидатов в один раздел сохраняется внутренняя привязка
к их исходным E-ID. Она строится только из фактически предложенных записей, а не
из входного metadata или ответа модели. Для выбранной цитаты packer сохраняет
всю исходную native-запись вместе с уже распознанными внешними условиями и
атомарными группами. Если такой пакет не помещается в прежний бюджет, цитата
не переносится отдельно от него. Это защищает контекст внутри исходной записи,
но не доказывает полноту всех условий из соседних записей или всего документа.

При валидных непустых подсказках применяется также мягкий штраф за сильную
лексическую избыточность; он не объявляет фрагменты одинаковыми фактами и не
удаляет кандидатов. Различия чисел, единиц, операторов, отрицаний, условий,
заголовков или редакций защищены; при неизвестной редакции сравнение отключено.
Этот сигнал не заменяет смысловую оценку достаточности ответа.

Чтение выполняется **не более одного раза на запрос**. При изменении пула или
возврате к исходной USER-задаче устаревшие подсказки снимаются без нового
модельного вызова. При ошибке, пустом пуле или отсутствии selector остаётся
обычный native packing; это не доказательство отсутствия сведений в библиотеке.
Pool-bound reading не передаётся writer как описание другого финального
snapshot: отдельный writer guide в этом режиме отсутствует. В trace видны
`experiments.prepack_source_reading`, `candidate_pool_only`, применение подсказок,
число выбранных абзацев и причина отказа; это решения, не скрытые рассуждения.

В `rounds[].retrieval.candidate_admission` видны число допущенных записей и
потери до reader из-за бюджета; образцы потерь содержат только хеш текста и
число символов. Порядок admission остаётся first-fit: reader не может восстановить
то, чего не получил. `prepack_source_reading.applied` отмечает реально сохранённую
дословную цитату с совпавшей привязкой и успешным native-сигналом, а не просто
валидный ответ reader. `native_preferred_passage_retention` отдельно показывает,
сколько native-пакетов не сохранилось. Эти счётчики не являются coverage score;
неполное сохранение и смысловую достаточность проверяйте раздельно.

Проверка контрактов без модели, сети и рабочей БД:

```powershell
.\.venv312\Scripts\python.exe -B -X utf8 -m pytest -q test_prepack_source_contract.py test_evidence_diversity.py test_evidence_diversity_contract.py
.\.venv312\Scripts\python.exe -B -X utf8 -m pytest -q test_prepack_retained_passages.py test_prepack_applied_truth.py test_inventory_selection_limits.py test_candidate_pool_boundary.py
```

Отдельно сохраняйте end-to-end ответы и исходный retrieval trace. Улучшение
одного synthetic/known-regression примера не означает принятие на рабочем
корпусе. Старый unassisted packer остаётся отдельной открытой проверкой.

## Представление источников без потери данных

Внутри corrective-контура writer получает компактный JSON. Повторяющиеся
строковые `file`, `file_name` и `file_path` могут быть вынесены из строк evidence
в `source_catalogue`; строка сохраняет `source_ref`, а инструкция объясняет эту
связь. Пользовательские ссылки по-прежнему строятся по E-ID, не по `source_ref`.

Это только представление: тексты, цитаты, формулы, порядок evidence, E-ID,
идентификаторы редакций и условия не удаляются и не нормализуются. Разные пути,
отсутствующее поле, `null` и пустая строка сохраняют свои значения. Каталог
применяется только при положительной экономии UTF-8 bytes с учётом добавленной
инструкции. При коллизии служебных имён остаётся обычный compact JSON.

Проверка обратного восстановления доказывает сохранность JSON-значений, но не
то, что модель правильно использовала сведения или стала отвечать быстрее.
При смене этого формата оценивайте готовые ответы заново на одинаковом корпусе
и отдельно проверяйте итоговый размер полного prompt, включая repair-запрос.
Сериализатор не сокращает текст ради лимита и не меняет output token budget.

```powershell
.\.venv312\Scripts\python.exe -B -X utf8 -m pytest -q test_prompt_payload.py
```

## Что меняется

Контур строит требования к ответу, собирает доказательства из доступных источников,
оценивает их полноту и при обнаружении пробелов выполняет ограниченный повторный
поиск. Затем формирует ответ и проверяет его утверждения и формулы.

- Исходная формулировка и контекст уточнений сохраняются. Просьба ответить кратко
  не должна менять категорию, компонент расчета или отрицательные ограничения.
- Планировщик получает названия и направления только доступных документов, а не
  их полные тексты. Этот каталог помогает определить предметную область, но не
  служит доказательством ответа.
- Отбор `coverage` учитывает части вопроса, сравниваемые категории, основной
  порядок и исключения. Совпадение заголовка не является единственным основанием
  для выбора документа.
- Полное тело документа не помещается в системный промпт. Передаются выбранные
  разделы и фрагменты с источниками и областями применения.
- У каждого доказательства есть внутренний `E-ID`. Он сохраняется при добавлении
  источников в следующих раундах. Пользователь получает человекочитаемый документ
  и ориентир, а не внутренний идентификатор.
  Ссылка связывается с UUID конкретной загрузки, а не с последним одноименным
  файлом. Для неоднозначного старого имени без идентификатора ссылка не
  подставляется наугад; это лучше неверного перехода на другой документ.
- Применяются прежние ограничения доступности документов проекта, чата и общей
  библиотеки. Повторный поиск не является разрешением читать чужие документы.
- Память проекта остается общей для его чатов, но сообщения соседнего чата не
  подмешиваются в запрос генерации. История текущего чата переносит намерения
  пользователя, не превращает старые ответы модели в новые доказательства.

Отрицательное ограничение пользователя относится к форме и предмету ответа, а не
к факту, который нужно искать в документах. Например, запрет описывать температуру
не должен запускать поиск инструкций скрытия температуры. Фактические вопросы
об исключениях из правил при этом сохраняются. Служебные ярлыки контекста диалога
не участвуют в оценке предметных совпадений, отрицание не захватывает следующую
строку запроса.

Числовые порядковые формы категории (`6-й ценовой категории`, `6-я ЦК`, включая
неразрывный дефис) нормализуются только для поиска и сопоставления области.
Исходный документ и обозначения формул не переписываются. Номер пункта, год или
величина в кВ не становятся номером ценовой категории.

Для запроса перечня типов/видов отбор отдельно сохраняет явно закрытый список
значений табличного поля в подходящем ближайшем разделе. Названия конкретных
файлов, заранее известные значения и их ожидаемое число не используются.
Обзорные смысловые группы не заменяют технический селектор. Сохраняются вся
подходящая таблица и окружающие нетабличные блоки исходного раздела: условие
может стоять после списка или в самостоятельной строке таблицы. Если этот пакет
не помещается, его значения не обрезаются молча. Это структурное замыкание;
полнота зависимостей из других разделов всё ещё требует отдельной проверки.

`inventory_enumeration_incomplete` означает известную неполноту такого перечня.
На сохранившемся фрагменте того же источника `missing_inventory_sections`
указывает его непереданные разделы. Если источник целиком не вошёл в контекст,
ограничение передаётся отдельно, без названия файла, разделов, ссылок или текста.
Оценка покрытия не может стать полной только потому, что модель одобрила
реальные цитаты. Эти ограничения участвуют и в ключе повторного использования
оценки; одинаковый текст с разными ограничениями не считается одной оценкой.
Диагностика ограничена и не является исчерпывающим списком пропущенных разделов:
в модель передаются до двух обезличенных представителей бюджетных ограничений
и до восьми ориентиров на весь набор доказательств. Слишком длинный ориентир
не переименовывается обрезкой. Признак неполноты сохраняется и при опущенных
подробностях; предупреждения не дублируются в двух полях промпта.

Закрытый табличный список подтверждает значения соответствующего поля, а не
универсальную полноту любых сведений о предмете. Классификация похожих полей,
применимость и смысл готового ответа по-прежнему требуют проверки.

План содержит `canonical_question` — самостоятельную формулировку предмета с
учетом уточнений. Она используется и для ранжирования, а не только для показа
плана. Исходный запрос остается среди поисковых формулировок; численные входные
данные проверяются по исходному пользовательскому тексту, не по пересказу модели.
План с придуманной категорией отклоняется, отсутствие нормализованного предмета
сохраняет исходный поисковый путь. Это не отменяет проверки доступа и не
разрешает использовать предположения планировщика как предметные факты.

### Поисковый предмет отдельно от требований к ответу

Планировщик может дополнительно вернуть `search_focus`: операцию и короткие
предметные фразы. Например, просьба «сравни лазерную и струйную печать, оформи
точной таблицей» содержит два независимых предмета поиска; слова об оформлении
не должны становиться обязательными словами каждого исходного абзаца.

Контракт находится в `search_focus.py`:

- `operation`: `lookup`, `enumerate`, `compare`, `calculate`, `procedure` или
  `locate_documents`.
- От 1 до 6 `subjects`; у каждого — `text` и до 3 `alternatives`.
- Каждая фраза — одна строка, до 120 символов и 12 слов. Неизвестные поля,
  некорректные типы, управляющие символы и превышение лимитов отклоняются, а не
  исправляются молчаливой обрезкой.
- `valid`, `absent` и `rejected` различимы в trace. Плохой необязательный focus
  не отменяет хороший остальной план. Недоступный planner оставляет прежний
  fallback на исходный запрос; дополнительных LLM-вызовов этот контракт не добавляет.

Фразы и их альтернативы используются для мягкого поиска, ранжирования и
резервирования места. Они не обязаны одновременно встречаться в одном фрагменте.
В сравнении сначала сохраняется доступный представитель каждого предмета,
затем — необязательная полнота одного семейства подразделов. `enumerate` включает
поиск явно закрытых табличных перечней без требования буквального слова «какие».
Список сохраняется вместе со всей таблицей и окружающими условиями; найденный
перечень конкретного поля не доказывает полноту всей темы.

Жёсткая область определяется отдельно по **исходному разрешённому контексту
пользователя** (`constraint_question`): явно выбранные документы, пункты,
категории, отрицания и прежние ACL/редакции. Сгенерированные canonical/focus
не получают права выбирать другой документ или снимать исключение. Исходный
запрос остаётся первой поисковой пробой, затем идут основные предметы и их
альтернативы в прежнем ограниченном бюджете проб. Полная задача и требования
сохраняются у writer и проверки покрытия.

При упаковке формул сохраняются смысловые существительные чистого предмета:
«цена» не должна исчезать, превращая запрос цены в поиск количества. Для
нескольких предметов пакеты формул чередуются в общем лимите шести пакетов.
Пользовательские именованные ориентиры участвуют в мягком ранжировании;
применимость ответа к конкретному объекту всё ещё требует проверки покрытия.

Это не семантический валидатор: правильная схема JSON не доказывает, что модель
верно поняла вопрос, выбрала хорошие синонимы или дала верный ответ. Отделение
search-query от исходного запроса соответствует общему подходу
[query rewriting](https://developers.openai.com/api/docs/guides/retrieval),
но само по себе не является результатом нашего benchmark. Ограничения схемы
не заменяют проверки смысла, что отдельно отмечено в
[Structured Outputs](https://developers.openai.com/api/docs/guides/structured-outputs).
Здесь работает наш локальный парсер; поддержка OpenAI Structured Outputs
у текущей Qwen не подразумевается.

Контракт действует только внутри `RAG_CORRECTIVE_PIPELINE=on`; отдельного нового
переключателя нет. По умолчанию production-путь не меняется. До общего включения
нужно проверить реальный planner и готовые ответы на том же корпусе. Результат
селекторного теста с вручную выделенными предметами — только проверка компонента,
не замер качества понимания вопроса или всего RAG.

Первичный план допускает исходный вопрос и до шести дополнительных формулировок.
После первой оценки разрешены **не более двух целевых дополнительных запросов**,
по одному на дополнительный раунд. Повторяющиеся формулировки исключаются.
Нижний retrieval-слой может дополнительно строить собственные детерминированные
пробы; два запроса не означают два HTTP-вызова к поисковому движку.

При `RAG_REFERENCE_EXPANSION=on` явно написанная в источнике отсылка может добавить
не более трех целевых фрагментов за один переход. Переход ограничен тем же
доступным физическим документом и совместимой редакцией. У цели сохраняются
исходная область применения и цитата-основание перехода: ссылка на расчет другой
категории не делает все условия этой категории применимыми к исходному вопросу.
Самостоятельные номера и ярлыки вроде «Где:» не считаются доказательствами.

Бюджет резервируется для всех отобранных слотов, а не только первых четырех.
Определяющее уравнение, обозначения его компонентов и ближайшие обязательные
условия защищены от вытеснения длинной таблицей или ранним использованием того же
символа в другой формуле. Это локальный переход зависимостей, а не алгебраический
вывод и не разрешение читать дополнительные недоступные документы.

Таблицы обозначений упаковываются по структурным строкам, сохраняя все ячейки
строки и связанные условия. Перенос Word внутри формулы не считается новой
строкой таблицы. Зависимости читаются из полной цепочки математических объектов,
а не только первого ее фрагмента. Если известное определение или его обязательное
условие не помещается, `definition_closure_incomplete=true` и
`missing_definition_symbols` передаются оценке полноты и генерации. Такая выдача
не может быть объявлена полной одним положительным ответом модели. Эти сигналы
участвуют в ключе повторного использования оценки внутри текущего запроса.

Для обзорного запроса компактный блок «область применения + следующий перечень
расчетных строк» переносится атомарно: до восьми элементов и 2000 знаков, не более
трех таких блоков на раздел. Узкий вопрос о величине сохраняет приоритет ее
определяющего уравнения. Непомещающийся атомарный блок не выдается частично за полный.

Для связанного перечня рассматривается до 12 непосредственных дочерних подразделов
в пределах 6000 знаков. Фактическая выдача все равно ограничена `top_k` и общим
бюджетом. У каждого пункта сохраняется свой ориентир. Если все пункты не поместились,
`evidence_family.complete=false` и список пропусков передаются проверке полноты.
Полнота пересчитывается после фильтрации области доступа и окончательного бюджета.
Простое определение не требует полноты соседних семейств подсистем. После
восстановления полного раздела прежние флаги его сокращения сбрасываются;
совпавшего адреса раздела недостаточно для подтверждения другой редакции —
проверяются идентификаторы редакции и хеш исходного текста.
Сама проверка подтвержденности отдельных утверждений не доказывает, что ответ
раскрыл все необходимые подразделы.

Роль раздела (`operative`, `amendment`, `change_log`) определяется по заголовку и
помогает мягкому ранжированию. Это не проверка юридической актуальности. Поправки
не исключаются из доступа; исторический запрос сохраняет их приоритет. Если
сопоставимого основного правила не найдено, одна лишь роль поправки не является
основанием выбросить единственный полезный источник.

Если доказательств нет, модель не вызывается для сочинения предметного ответа.
Если подтверждена только часть требований, следует отвечать на подтвержденную
часть и обозначать пробел, а не выдавать частный случай за полный ответ.

нужны для конечного окна модели и не восстанавливают снятый лимит длины ответа.

## Граница кеширования

`legacy` сохраняет прежнюю retrieval-first схему кеша: переиспользование ответа
допускается только при выполнении проверок общей области, контекста и системного
промпта. Документы проекта/чата и история не должны попадать в общий кеш ответов.

Полный `corrective` сейчас **не читает и не записывает общий кеш готовых ответов**.
Его результат и trace возвращают `from_cache=false`. Это сознательная граница
первого релиза, а не обещание одинаковой задержки с прогретым legacy-кешем.
Отключение кеша ответов не означает отключения кешей embedding, моделей,
распознавания изображений или других технических кешей нижних уровней.

Для честного сравнения не учитывайте старые ответы из чата как новый прогон.
Runner ниже передает пустой набор `shared_cache_sources` и не использует общий
кеш готового ответа для сравниваемых вызовов.

## Как читать trace

Trace описывает решения и происхождение данных, а не скрытую цепочку рассуждений.
Он доступен через `last_retrieval_trace()` у экземпляра агента после запроса и
в поле результата `retrieval_trace`. Состояние агента привязано к потоку запроса,
чтобы параллельные чаты не получали чужой последний trace.

| Поле | Что проверять |
| --- | --- |
| `mode` / `version` | Новый запрос действительно прошел `corrective`, а не legacy |
| `plan.requirements` | Не потеряны части вопроса, сравниваемые категории и требование полного перечня |
| `plan.queries` | Сохранен исходный вопрос; нет придуманного сужения до категории |
| `plan.exclusions` | Отрицательные ограничения не перепутаны с предметными фактами; стиль конечного ответа определяется исходным вопросом, а не JSON-контрактом планировщика |
| `plan.fallback` | План не удалось надежно получить; использована исходная формулировка |
| `plan.search_focus` | Короткие поисковые предметы и операция; не факты и не область доступа |
| `plan.search_focus_status` / `search_focus_reason` | `valid`, `absent` или `rejected` с безопасным кодом причины |
| `rounds[].queries` / `retrieved` | Какие запросы инициировали раунд и сколько фрагментов вернулось |
| `rounds[].evidence_ids` | Какие доказательства реально переданы на оценку |
| `rounds[].coverage` | Покрытые и непокрытые требования, конфликты, предложенные целевые запросы |
| `rounds[].retrieval` | Фактический query plan, видимые кандидаты и финально выбранные разделы нижнего retrieval |
| `rounds[].retrieval.constraint_question` | Неизменённый пользовательский контекст, по которому применялись жёсткие ограничения |
| `context[].evidence_family` | Полнота связанного перечня, реально оставшиеся/пропущенные подразделы; полный объект хранится на одном сохранившемся элементе |
| `context[].selection_signals` | Резерв payload, зависимые формулы и непоместившиеся атомарные блоки; это диагностика, не смысловая оценка |
| `verification.initial` / `after_repair` | Проверка исходного ответа и результат единственной попытки исправления |
| `verification.partial_answer` | После исправления пришлось убрать явно неподтвержденные места |
| `verification.publication` | Какой черновик дал частичный ответ: `repair_safe_partial`, `primary_safe_partial` либо `neutral`; число сохранённых утверждений и хеши именно выбранного черновика и его отчёта |
| `verification.skipped` | Например, `no_evidence`: предметная генерация не выполнялась |
| `calculations.rules` / `diagnostics` | Разрешенные ограниченные расчеты и причины, почему другие не удалось проверить |
| `completions` | Назначение вызова, длительность и состояние thinking-ветки/fallback |
| `corpus_snapshot` | Локальный маркер снимка docstore; это не криптографический хеш всего корпуса |
| `elapsed_s` / `coverage_complete` | Время контура и мнение оценки полноты, не сертификат истинности ответа |

В `coverage` требование считается покрытым только при известных E-ID и реально
существующих абзацах. Проверяющая модель указывает адрес исходного абзаца,
а программа сама извлекает дословную цитату. Аналогично утверждения ответа имеют
стабильные C-ID, поэтому модель не должна перепечатывать Markdown и длинные цитаты.
Заголовки Markdown и отдельные жирные заголовки передаются отдельно как H-ID:
проверка утверждения включает упорядоченный контекст его заголовков. Это сохраняет
условие вроде «только в аварийном режиме», если подтверждённый пункт пришлось
извлечь из частично неверного ответа. Заголовок без последующего текста не
освобождается от проверки. Примеры синтаксиса в промптах используют только
существующие ID текущего контекста, а не вымышленный первый источник.
Неизвестные адреса отклоняются. Повторная выдача того же набора доказательств не
запускает одинаковую оценку заново в пределах запроса. Это проверяет происхождение цитаты; смысловую применимость
продолжает оценивать модель, которая может ошибиться.

Неоднозначность пользовательского термина следует обозначать, не заменяя вопрос
формально похожим термином. Противоречия единиц измерения в оригинале требуют
явного предупреждения: точная транскрипция формулы не дает права придумать
пересчет или молча выбрать удобную размерность.

В `verification` отдельно смотрите `assessment_complete`, число
`unassessed_claim_count` и предупреждения. Если проверяющая модель недоступна,
возвращает неполный список или не проверила часть прозы, ответ нельзя считать
полностью подтвержденным только потому, что `needs_repair=false`.

`initial` и `after_repair` описывают соответствующие черновики, а не автоматически
подтверждают опубликованный текст. Для частичной публикации смотрите отдельное
поле `publication`: `source_draft_sha256` и `source_report_sha256` связывают
выбранные фрагменты с конкретной версией и её проверкой. Значение
`whole_answer_certified=false` не следует трактовать как проверку всего ответа.

Trace и сырые benchmark-отчеты могут содержать вопросы, тексты документов и
приватную память проекта. Ограничивайте доступ так же, как к исходным документам;
не публикуйте их целиком в общих логах или внешних чатах.

## Формулы: что проверяется и что не гарантируется

- Проверяются наличие разрешенного источника, цитата и структура формулы.
  Нельзя добавлять слагаемые, переставлять индексы или заменять кириллицу похожей
  латиницей только ради успешного рендера.
- Поддерживаются ограниченные арифметические выражения с явно заданными
  значениями символов. Произвольный Python или код из документа не исполняется.
- Численный результат не подтверждает предметную применимость формулы.
  Размерности, преобразование единиц, сложные условные алгоритмы и неоднозначные
  исходные значения требуют отдельной проверки; диагностический отказ не равен
  доказательству, что формула неверна.
- OCR-формулы с предупреждением не объявляются точными документальными
  формулами. Мелкие индексы и знаки необходимо сверять с оригиналом.
- Корректный KaTeX означает только правильный синтаксис отображения, не смысловую
  правильность выражения.

После одной неудачной попытки исправления явно неподтвержденные формулы или
утверждения удаляются по проверенным границам фрагмента. Непроверенная проза
не превращается автоматически ни в ложь, ни в подтвержденный факт.

Ошибка привязки цитаты у проверяющей модели означает незавершенную проверку, а не
ложность самого ответа. Только из-за такой ошибки ответ не переписывается и его
факты не удаляются. Служебный JSON с текстовым полем `answer` раскрывается до
проверки; непригодная вложенная обертка получает одну попытку исправления и не
показывается пользователю как готовый предметный ответ.

Для корректно разобранных native Word `[MATH: ...]` строится каталог готовых
LaTeX-записей с проверкой обратного сравнения знаков и индексов. Модель может
копировать подходящую запись, не переписывая индексы. Каталог не исправляет
опечатки оригинала, не реконструирует OCR и не доказывает применимость формулы.

Граница `[MATH]` в Word не обязательно завершает уравнение. Последовательные
математические объекты одного абзаца с явными операторами собираются целиком;
префикс длинной суммы не подтверждается как отдельная полная формула. Неизвестный
оператор или оборванное продолжение не разрешают численный расчет по префиксу.
Если сложная запись выходит за возможности строгого сравнения, результат —
`unassessed`, а не доказанная ошибка: автоматическое удаление не применяется,
но весь ответ не объявляется полностью проверенным.

## Сравнение на одном корпусе

Runner `evals/run_pipeline_benchmark.py` работает внутри настроенного RAG-runtime.
Он не регистрирует пользователей, не создает чаты, проекты или документы и не
меняет их области доступа. В обоих наборах используется одна область:
**`ready-global-only`** — только готовые общие документы, без файлов проекта/чата.
Технические кеши и прогрев модели при этом могут обновляться.

Наборы:

- `evals/production_golden.jsonl`: 130 вопросов для сравнения retrieval.
- `evals/tester_oct21.jsonl`: 17 вопросов, включая уточнения, требования ручной
  проверки и отложенные перефразировки. Не используйте отложенные кейсы как
  список специальных условий в коде.

Перед прогоном зафиксируйте SHA приложения, выбранную модель, настройки
reranker/embedding, список и хеши готовых общих документов. Корпус между режимами
не изменяйте. Отсутствие ожидаемого документа — проблема состава стенда, а не
успешный отказ RAG. Запускайте последовательно, чтобы нагрузка разных режимов не
искажала задержку.

Из канонического PowerShell после подготовки образа и запуска стека:

```powershell
docker compose -f compose.yaml --env-file .env exec -T app python evals/run_pipeline_benchmark.py --dataset evals/production_golden.jsonl --mode legacy --output /app/.data/evals/oct21-130-legacy.json
docker compose -f compose.yaml --env-file .env exec -T app python evals/run_pipeline_benchmark.py --dataset evals/production_golden.jsonl --mode coverage --output /app/.data/evals/oct21-130-coverage.json
docker compose -f compose.yaml --env-file .env exec -T app python evals/run_pipeline_benchmark.py --dataset evals/tester_oct21.jsonl --mode legacy --answers --output /app/.data/evals/oct21-17-legacy.json
docker compose -f compose.yaml --env-file .env exec -T app python evals/run_pipeline_benchmark.py --dataset evals/tester_oct21.jsonl --mode corrective --answers --output /app/.data/evals/oct21-17-corrective.json
```

Режим `coverage` здесь предназначен для retrieval-only сравнения. Для проверки
полного нового ответа используйте `corrective`, а не комбинацию
`coverage --answers`. Полный `corrective` вызывает генерацию независимо от
`--answers`; флаг в примере делает назначение прогона явным.

Отчеты сохраняются в смонтированном `/app/.data/evals`, вне исходников. Runner
пишет их после каждого вопроса, поэтому можно отличить промежуточный отчет от
завершенного по `summary.completed`. Для безопасного короткого smoke-прогона
добавьте `--limit 3` и другое имя выходного файла. Не смешивайте его с полным
baseline.

### Одинаковый пользовательский preset и проверяемый запуск

Для сравнения готовых ответов передайте в оба режима один и тот же UTF-8 файл
через `--system-prompt-file` и, при необходимости, `--system-prompt-label`.
Runner передаёт текст без нормализации переносов/пробелов; BOM не становится
частью промпта. В отчёте остаются хеш исходного файла и хеш переданного текста,
а не содержимое preset. Сравните их с реально выбранным production preset:
одноимённая локальная заготовка этого не доказывает. Без файла отчёт явно
помечает preset как `runtime-default-unverified-preset`. Это не меняет настройки UI.

Файл промпта защищён от перезаписи отчётом. Для retrieval-only режима override
отклоняется: там он не мог бы влиять на ответ. Ошибки отдельных вопросов сохраняются
в отчёте и приводят к ненулевому коду выхода batch; `0` всё равно означает только
отсутствие таких ошибок, не правильность смысла. `corrective` больше не может тихо
работать через адаптер без явного контракта `pipeline_mode`.

Для изолированного runtime проверяйте до генерации:

1. Все writable-пути находятся в выбранном приватном QA-каталоге. Вопросы, gold,
   конфигурация и отчёты не перезаписывают друг друга.
2. Хеш docstore совпадает с замороженным; каждый разрешённый документ имеет активный
   непустой текст. Один alias-список не доказывает наличие корпуса.
3. Настройки каждого режима заданы явно: embeddings, Qdrant-коллекция, reranker,
   reader, scope, отсылки, thinking и бюджеты. Чужие наследованные значения не
   должны молча выбирать вариант опыта.
4. Планировщик обращается к тому же приватному bridge. `/api/tags` недостаточно:
   этот route может возвращать статический ярлык. Проверьте реальный health,
   ID модели и размер окна upstream; bridge может игнорировать поле model в запросе.
5. Все выбранные вопросы действительно завершены без ошибок в требуемом режиме.
   Отдельно посчитайте `valid/absent/rejected` для focus; валидная структура не
   доказывает полезность выделенного предмета.

Чистые проверки формы входов/исполнения находятся в
[evals/runtime_preflight.py](../evals/runtime_preflight.py). Они не создают
production-настройки и не являются сертификатом качества; семантическое
тождество векторной коллекции нельзя подтвердить только её именем или metadata.
Синтетический отбор с вручную заданным focus, локальная модель другой величины,
полный backend runtime и браузерные сценарии — отдельные уровни проверки.

### Исходная задача отдельно от поисковой гипотезы

История намерений текущего чата выбирается из PostgreSQL отдельно от общей ленты
проекта: только полные, неудалённые USER-сообщения разрешённого текущего чата,
с их ID и стабильным порядком `(created_at, id)`. Сообщения соседних чатов и
длинные ответы ассистента не расходуют это окно. Прежняя проектная лента остаётся
доступной как отдельная выдача; она не подставляется вместо пустого окна чата.
Для совместимости low-level callers без нового поля могут передать прежнюю
ленту, но из неё также отбираются только USER-сообщения текущего чата.

В `retrieval_trace.conversation_context` проверяйте отдельно:

- `history_window`: источник окна, число USER-сообщений, лимит и факт усечения
  выборки БД; ID реально использованных сообщений находятся в `source_message_ids`;
- `writer_history_window`: сколько сообщений дошло в текст генератора,
  сколько пропущено или обрезано и сколько символов заняло представление.

Прежний текстовый бюджет генератора — 1800 символов на сообщение и 12000 на
историю — не является полной долговременной памятью. При любом усечении
генератор получает предупреждение. Даже если окно БД полное, текст генератора
может быть частичным; наличие ID и успешная выборка не доказывают понимание
уточнения или полноту ответа. Лексическое разрешение уточнений и отмена прежних
ограничений требуют отдельной смысловой приёмки.

В corrective-пути точный вопрос и разрешённый USER-контекст передаются одним
неизменяемым `UserTask` отдельно от `SearchPlan`. Модельный `canonical_question`,
требования и focus помогают искать, но не вправе переименовать неизвестный
предмет. Пользовательский контекст определяет намерение, а не доказывает факты.
Один объект задачи проходит coverage, reader, writer, judge и существующий repair.

Coverage теперь проверяет две независимые вещи: покрыты ли требования плана и
соответствуют ли найденные сведения исходной задаче (`task_alignment`). Для
`matched` нужны существующие passage IDs. Отсутствующий/невалидный вердикт
становится `unassessed`, а не доказательством отсутствия сведений. При расхождении
один из уже разрешённых поисковых раундов может повторить исходный запрос без
модельного focus и canonical-ранжирования. Повтор ограничен одним разом, даже
если исходный запрос уже был выполнен; неизменный контекст не переоценивается.

Judge отдельно оценивает поддержку источником и соответствие задаче для каждого
неизменяемого C-ID. Факт может быть подтверждённым, но посторонним. Неопределённость
не объявляется ложностью. Неполная проверка в explicit-task пути задействует
существующий единственный repair; после него публикуются только точные фрагменты
с подтверждённой поддержкой и `matched`-оценкой либо нейтральная неопределённость.
Сначала выбираются проверенные фрагменты исправленного черновика. Если таких нет,
можно сохранить проверенный фрагмент первоначального ответа по его собственному
отчёту. Версии не смешиваются, ссылки не заимствуются у удалённых соседних фраз,
новые факты не дописываются. Тем самым неудачное исправление не обязано уничтожать
уже проверенный ответ. Это не отменяет обозначения оставшихся пробелов и не
доказывает полноту результата.
Новый обязательный model call не добавлен, но ранее не проверенный ответ теперь
может потребовать этот предусмотренный repair. Рост числа отказов на вопросах
с доступным ответом — регрессия, её обязательно измерять отдельно.

Reader-снимок привязан также к точному контексту задачи: одинаковые E-ID и
короткий вопрос с другим antecedent не позволяют переиспользовать прежнее чтение.
Writer получает контекст задачи один раз вне предварительной выборки источников.
Прямые low-level API без `user_task` сохраняют legacy-семантику; штатный
`run_corrective` всегда передаёт задачу. При выключенном corrective production-путь
не меняется. Эти проверки — ограниченные модельные оценки, не доказательство
семантической истины и не замена корпусной приемке.

### Явно названные источники и квота доступного контекста

Имя источника разрешается только по каталогу документов, видимых запросу.
Точное имя файла, путь или нормализованный alias не расширяются совпадением
по общему году, версии или части делового описания. Отдельно названный второй
документ сохраняется, даже если ссылка на него стоит после первого filename.
Короткий буквенно-числовой ID должен подтверждаться каталогом. Заголовок без
расширения сам по себе не делает обычную тему вопроса жёсткой ссылкой: нужны
локальное именование, кавычки или связанный перечень названных документов.

Ограничение текущего API: неизвестное имя и отсутствие явной ссылки пока дают
одинаковый пустой набор совпадений. Это не доказывает отсутствие документа или
полноту поиска. Каталог и итоговые ACL продолжают ограничивать доступ; этот
matcher не заменяет проверку прав.

В body-поиске область доступных источников и исключения применяются **до**
расчёта редкости и обрезки кандидатов. Недоступные фрагменты не должны занимать
весь лимит и вытеснять доступный ответ. Та же область применяется при повторном
body-bootstrap внутри `select_v2`; итоговые проверки разделов, редакций и
релевантности не отключаются. Общий индекс не перестраивается и не мутируется
при переключении чатов. Для low-level helper `allowed_sources=None` сохраняет
прежнюю семантику без ограничения; пустой `set()` запрещает всё. Это различие
не является способом обхода штатной авторизации приложения.

Автоматическое дополнение формулой не должно превращать обычное текстовое
правило или UI-путь в блок KaTeX. Оно проверяет запрос, синтаксическую форму
кандидата и подтверждение исходным фрагментом; непригодный первый кандидат не
скрывает следующий подтверждённый. Синтаксический разбор ничего не исполняет.
Он не доказывает математическую истинность или соответствие формулы задаче:
эти свойства требуют отдельной смысловой проверки ответа.

не меняет ACL и не заменяет его штатное ограничение размера/срока хранения.

### Ссылка не должна менять ориентир в документе

Преобразование E-ID в человекочитаемый источник не выбирает раздел заново.
При явном ориентире сначала ищется точное нормализованное совпадение; формульная
эвристика не вправе заменить его соседним пунктом. Если ориентир неоднозначен,
сохраняется исходный текст, а не первый попавшийся раздел. Ссылка на документ
без точного пункта допустима только при однозначном URL. Номер страницы не
придумывается. Эти проверки отвечают за честность ссылки, но не заменяют оценку
того, действительно ли источник подтверждает утверждение.

### Разные части запроса не должны вытесняться повторяющимся обзором

Отбор сохраняет локальное место исходной записи в уже выполненных поисковых
запросах до объединения результатов. Эти ранги живут только внутри текущего
вызова: их нельзя передать через метаданные загруженного документа или сохранить
на общем экземпляре агента. При повторном поиске создаётся новый контекст рангов.
Штатный corrective callback явно передаёт его внешнему сборщику доказательств.

После фильтрации доступных источников, редакций и применимости сборщик учитывает
предельный прирост разнообразия поисковых запросов: несколько почти одинаковых
обзоров не должны занять все места вместо фрагментов, занявших первые позиции
в разных уточняющих поисках. Исходный запрос имеет вес 1, все дополнительные
запросы вместе — не более 1. Ранги нескольких каналов одного запроса не суммируются.
Разные числа, отрицания, операторы и дополнительные признаки не становятся
эквивалентными только из-за совпадения части слов.

Это мягкий приоритет, а не подтверждение факта и не новая область доступа.
Он не отменяет структурные условия и атомарные пакеты; прирост засчитывается
только после реального сохранения исходной записи с точной редакцией и полным
текстом. Исходная identity использует полный raw-текст; при штатном удалении
структурных `[SECTION:…]` проверяется вся native-проекция записи, без этих маркеров,
а не отдельная совпавшая фраза. Это не утверждение о побайтовом сохранении raw.
Единственный запрос и отсутствие дополнительного прироста сохраняют
обычный порядок отбора. Новых поисковых/модельных вызовов, увеличения `top_k`
или бюджета контекста этот механизм не добавляет.

Повторная сборка использует request-local sidecar receipts: точная identity
реально сохранённого native-пакета связывается с его исходными записями.
Служебный E-ID, добавленный между сборками, эту identity не заменяет. Receipt
создаётся только после фактической упаковки из текущей eligible ancestry,
не для произвольного bootstrap из индекса и не по полям загруженного документа.
На запрос допускается не более 128 разных receipts; новая retrieval-попытка
создаёт новый контекст. В witness индекса нет пользовательских поисковых рангов.

Строгое сравнение исходной identity не ослабляется. Единственный специальный
construction witness — отсутствовавший `file_path` может получить однозначный
уже известный native-путь той же записи. Явный `null`, пустая строка, другой путь,
тип или редакция не считаются отсутствием. Неполный текст/условие не даёт receipt.

### Внутренние ссылки и контекст заголовков при проверке ответа

Если writer вернул `[E1:P2]`, ссылка может быть преобразована в `[E1]` только
по реальному абзацу текущего, уже отфильтрованного набора доказательств. В группе
ссылок проверяется каждый элемент: неизвестная ссылка оставляет всю группу
непреобразованной и не должна скрыться за соседним корректным E-ID. Код, формулы
и строковые литералы не переписываются как служебные ссылки. Это нормализация
синтаксиса, а не доказательство соответствия утверждения источнику.

Нормализуется целиком каждый новый черновик, включая единственный repair, до
разбиения на C-ID, вычисления смещений и hash ответа. Старые оценки после
переписывания черновика повторно не используются. Диагностика содержит только
количество преобразований и ошибок, не копию отклонённого ответа.

В примерах JSON для judge всегда показывается `context_ids`: пустой список для
утверждения без заголовка либо реальные H-ID его заголовков в исходном порядке.
Вступление без заголовка не должно скрывать схему последующих утверждений.
H-ID — контекст заголовков **ответа**, а не идентификатор источника или абзаца.
Отсутствующий, чужой или неверно упорядоченный обязательный H-ack по-прежнему
не позволяет считать утверждение проверенным.

При выпуске этих изменений namespace answer cache меняется на
`v40-query-rank-and-citations-2026-10-22`. Записи v39 не переиспользуются; штатный
TTL и private/shared ограничения не меняются, массовая очистка не нужна.
Перезапустите все workers, включая UI/Rust boundary: импортированная константа
версии не обновляется в уже работающем процессе сама.

Concept-seed расширение также не должно заранее оставлять только файл с известным
суффиксом. До его ограниченной квоты применяются исходная пользовательская область,
исключения, применимость и предпочтение редакции; имя `*_r12_rag.md` не отменяет
другие подходящие записи. Это касается seed-channel, а не гарантирует полноту
всех каналов поиска. Старые filename-family квоты legacy-пути требуют отдельной
приёмки и не считаются устранёнными этой правкой.

### Исходный вопрос важнее поисковой гипотезы

`TaskIntent` явно отделяет неизменённый `UserTask` от предположений планировщика.
В planning, coverage и writer запрос «проверить/сравнить/разделить» не означает
«доказать цитируемое предположение». Requirements — открытые поисковые вопросы,
не обязательная истинность тезиса и не самостоятельный критерий приёмки.
Coverage/writer получают `task_intent_contract` без второй копии исходного вопроса.
`semantic_validation=not_performed` честно отмечает: сохранение текста и правильные
ID сами по себе не доказывают понимание модели. Нового модельного этапа или
обязательной схемы ответа эти метаданные не добавляют.

### Допуск кандидатов до ограничения контекста

`assign_evidence` различает полный текст и типизированные поля native identity,
включая source/revision/version, путь и hash. Отсутствие поля, `null`, `1`, `1.0`
и `true` не схлопываются. При непрозрачной identity равенство не считается
доказанным: новая запись получает новый request-local ID, даже если вызывающий
код повторно использовал изменённый Python-объект.

Экспериментальный `RAG_QUERY_DIVERSE_ADMISSION=on` меняет порядок допуска
кандидатов **до** first-fit ограничения. По умолчанию `off`. Приоритет использует
только request-local ранги уже выполненных запросов и предельный прирост
разнообразия на символ. Исходная запись должна помещаться целиком. Неподходящие
по размеру, не связанные с рангами и оставшиеся записи сохраняют относительный
fallback-порядок; один запрос не меняет исходный порядок.

Это разнообразие поисковых списков, **не смысловое покрытие** частей вопроса.
Механизм не создаёт новый поиск, не находит отсутствующий в pool пункт и не
гарантирует выбор определения вместо исключения. Включайте его только после
сравнения полного ответа на своём корпусе. Флаг не включает prepack/corrective
автоматически и сам по себе не изменяет конфигурацию уже работающего сервиса.

Callback получает точный `UserTask` и копию уже разрешённых кандидатов. Разрешена
только полная перестановка: нельзя добавлять/удалять записи, менять текст,
метаданные или multiplicity. Проверяется весь типизированный record. Невалидный
результат/исключение возвращает исходный порядок, без нового вызова модели;
`candidate_ordering` в trace содержит только status/reason/счётчики, не документы
или текст ошибки. После валидации используются исходные native-объекты.

### Управляемое чтение структуры документов

Экспериментальный `RAG_DOCUMENT_NAVIGATION=on` добавляет ограниченную навигацию
в corrective-контуре; по умолчанию `off`. Сам флаг не включает corrective и не
переключает уже запущенный сервис. При включении первичный retrieval возвращает
native candidates до локальной упаковки, независимо от prepack-reader флага.

Provider строится из отдельных `SectionEvidenceIndex.body_items`, а не из
склеенных `.sections`. Сначала применяются действующие фильтры исходной задачи:
область пользователя/проекта/чата, исключения, выбранные документы/пункты,
тип источника и категории. `source_aliases={}` по-прежнему означает пустую
область, не отсутствие ограничения. Исторические редакции не удаляются новой
эвристикой: сохраняется существующее soft-предпочтение, разные source identity
остаются разными документами. Обновлённый docstore создаёт новый снимок.

Внутренние инструменты:

| Инструмент | Что возвращает | Чего не доказывает |
|---|---|---|
| `list_documents` | Страницу доступных физических источников/редакций | Содержание документа |
| `outline` | Исходные записи и заголовки, включая headingless | Наличие нужного ответа |
| `search` | Лексические совпадения и preview до 300 символов | Истинность или применимость |
| `read` | Полную исходную native-запись | Полноту ответа/вывод модели |

Handles и cursors принадлежат только текущему private snapshot и не являются
пользовательскими ссылками. Их нельзя передать через metadata файла или другой
запрос. Full read сохраняет исходные текст и JSON-native metadata; preview
никогда не становится доказательством. Модель задаёт только разрешённые
действия, не shell-команды, не ACL и не собственный текст источника.

Одна навигационная попытка на corrective-запрос: не более трёх completion
callbacks, четырёх действий за ход и шести полных записей. Общий размер чтения
ограничен текущим `max_context_chars`; непомещающаяся запись отклоняется целиком.
Внутренний prompt также имеет защитный предел 96k символов. Это не гарантия
token fit провайдера; оценку токенов и transport limits проверяйте отдельно.

Прочитанный ограниченный пакет сохраняет приоритет до финального контекста,
чтобы второй heuristic packing не выбросил уже изученные определения. Остаток
бюджета заполняет обычный native selector. Число records может отличаться от
обычного `top_k`, но общий character cap не растёт. Прежние scope/coverage,
формульные и grounding проверки не отменяются. При mismatch/uncertain alignment
приоритет пакета отзывается перед восстановлением поиска по исходной задаче;
новой навигационной попытки это не создаёт.

Ошибки JSON/инструмента не становятся текстом доказательства. Завершённые
native reads могут сохраниться после ошибки позднего optional-этапа, но не
получают сертификат полноты. `document_navigation` в публичном trace содержит
только разрешённые счётчики, статус, отзыв приоритета и фактическое сохранение
записей. Содержимое документов, произвольный error message и private handles
туда не копируются. `coverage_certified` всегда `false`.

Network-free проверки:

```powershell
.\.venv312\Scripts\python.exe -B -m pytest -q test_document_navigation.py test_source_navigation.py test_navigation_boundary.py test_navigation_recovery.py
```

### Частичный ответ должен оставаться целым

При публикации verified partial сохраняются целые исходные абзацы, элементы
списка, таблицы и формулы с синтаксически зависимой вводной фразой. Если часть
такого блока не прошла прежние строгие проверки C-ID, ссылки и task relevance,
блок не публикуется частями. Поддержанный независимый абзац под тем же заголовком
может сохраниться. Lazy continuation списка относится к исходному элементу,
даже без отступа; нельзя удалить условие и оставить следствие без него.

Ссылки соседнего предложения не заимствуются. Writer отдельно получает правило
ставить источник непосредственно у самостоятельной формулы/пункта/строки.
Атомарность предотвращает оборванный Markdown, но не удостоверяет смысл:
положительное решение judge всё ещё требует независимой проверки качества.

Только в изолированном эксперименте с явным аргументом
`citation_repair_contract=True` у `run_corrective`/`verify_grounding` и переданной
`user_task` собственная ссылка проверяется уже до исправления, а не только при
публикации: отсутствие ссылки у C-ID даёт локальную проверку
`kind=citation_policy`, `status=invalid_citation`. Семантический статус
`judge_supported` при этом не заменяется на «ложно»: подтверждение факта и
соблюдение политики ссылок — разные условия. Ошибка привязана к исходному
диапазону; отдельно процитированный повтор того же текста не блокируется.
По умолчанию аргумент равен `False`; `RAGAgent`, веб-API и переменные окружения
не включают его. Обычные вызовы сохраняют прежнюю политику; положительные
синтетические тесты не дают основания включать эксперимент без quality gate.

При том же явном экспериментальном аргументе исправительный запрос получает
точный полный нормализованный черновик в JSON
`untrusted_previous_answer`. Он помечен как непроверенный кандидат, не источник
и не инструкции. Полученный новый ответ заново проверяется. В обычном пути
передача полного черновика не добавляется.

Независимо от эксперимента, если опциональный
запрос исправления падает, например из-за тайм-аута или контекстного ограничения
провайдера, выполняется прежняя строгая публикация подтверждённой части первого
ответа: без повторных попыток и без выдачи непроверенного черновика целиком.
Trace содержит только класс ошибки в `verification.repair_error.error_type`,
не текст транспортной ошибки; успешная повторная проверка не имитируется.
Критические `BaseException`-границы не подавляются. Это не проверка полноты
финального ответа и не доказательство качества 9/10.

Проверки этих границ без сети и модели:

```powershell
.\.venv312\Scripts\python.exe -B -m pytest -q test_candidate_ordering.py test_candidate_admission_contract.py test_admission_runtime.py
.\.venv312\Scripts\python.exe -B -m pytest -q test_task_intent.py test_task_intent_integration.py test_atomic_publication.py
.\.venv312\Scripts\python.exe -B -m pytest -q test_citation_policy_repair.py
```

При полном локальном сборе, включающем сохранённые версии тестов в
`output/diagnostics`, используйте `python -B -m pytest --import-mode=importlib`:
так одинаковые имена архивных test-модулей не конфликтуют. Не удаляйте
сохранённые артефакты ради устранения этой ошибки сбора.

### Приемка результата

Source/locator recall отвечают на вопрос «дошли ли нужные документы/разделы до
контекста». Они не доказывают, что ответ выделил основное и корректно применил
найденное. Сверяйте сырые ответы с `review_requirements` и оригиналами документов:

1. Есть основное правило, а не только редкое исключение.
2. Закрыты все требуемые категории и компоненты; перечень не назван полным,
   если извлечен только вводный обзор.
3. Уточнения сохраняют предмет предыдущего вопроса и исключают ненужный компонент.
4. Ссылки подтверждают конкретные утверждения, формулы и условия их применения.
5. Не добавлены отсутствующие факты, коэффициенты и слагаемые.
6. Учтены непроверенная проза, ошибочные отказы, конфликты и время ответа.

Рост доли отказов при наличии нужных сведений не считается улучшением точности.
Отдельно проведите пользовательские проверки с документами проекта и чата,
переключением общей области, параллельными чатами и обновлением страницы:
область `ready-global-only` эти сценарии не покрывает.

В этой инструкции результаты прогонов намеренно не зафиксированы. Решение о
включении принимает оператор по полным артефактам конкретного релиза и ручной
приемке, а не по факту наличия нового алгоритма.

## Воспроизводимая сборка интерфейса

Production UI собирается из того же коммита и **чистой установки по
`ui/package-lock.json`**. Штатный `deploy/nginx/Dockerfile` выполняет `npm ci` в
отдельном builder-слое. Для source-only overlay нельзя брать `ui/dist` после
обычного `npm run build` из непроверенного локального `node_modules`: symlink/pnpm
дерево может отличаться от lockfile, даже если TypeScript и тесты прошли.

Если требуется отдельный UI-артефакт, распакуйте отслеживаемый `ui/` из конкретного
коммита в новый build-каталог внутри канонического workspace, выполните там
`npm ci`, `npm ls --all`, `npm test` и `npm run build`. Не удаляйте существующее
пользовательское дерево зависимостей для получения чистой сборки. Сохраните
коммит, хеш артефакта и фактические версии зависимостей в приватном журнале релиза.

Проверка редактора с замоканными UI-примитивами подтверждает только контракты
приложения. До выкладки нужен smoke настоящего runtime редактора; после выкладки -
вход, ввод сообщения, две вкладки, refresh и проверка browser console. Ошибки
`getSnapshot`/`Maximum update depth exceeded` блокируют UI-релиз. При такой
регрессии откатывается только собственная новая UI-сборка, а не рабочие индексы
или модели. Новая версия интерфейса не считается проверенной по одному build.
