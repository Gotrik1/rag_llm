# Контроль качества: поиск отдельно от генерации

Этот эксперимент определяет, на каком этапе теряется правильный ответ. Он не
включает экспериментальный RAG для пользователей и не является приёмкой релиза.
Основная методика приёмки остаётся в [QUALITY_EVALUATION.md](QUALITY_EVALUATION.md).

## Что сравнивается

Для одного вопроса выполняются два первичных вызова генератора:

- `actual`: контекст из сохранённой трассы RAG;
- `oracle`: отдельно отобранные и проверенные исходные разделы и абзацы.

Oracle содержит текст источников, а не написанный человеком правильный ответ.
В обоих вариантах одинаковы вопрос, сохранённый план, инструкции, модель,
параметры генерации и политика бюджета. Фактовая рубрика не передаётся модели.
Переносимые метаданные и порядок доказательств должны быть записаны в протоколе.

Проверка полноты, самопроверка ответа и исправляющий вызов отключены **в этом
изолированном эксперименте**, одинаково для обеих веток. Иначе результат мог бы
объясняться разным числом попыток, а не составом контекста. Ответ из старого
отчёта после исправлений нельзя считать контрольной веткой этого сравнения.
Состояние рабочего сервиса не меняется.

## Утилита

[evals/oracle_ablation.py](../evals/oracle_ablation.py) разделяет подготовку и
вызов модели. Проверить доступные параметры без сетевых запросов:

```powershell
python evals/oracle_ablation.py prepare --help
python evals/oracle_ablation.py run --help
python -m pytest -q test_oracle_ablation.py
```

`prepare` принимает `--archive`, `--oracle`, `--docstore`, `--aliases`, новый
`--output`, а также наблюдаемые `--runtime-id` и `--model-revision`. Все вопросы
архива должны иметь ровно одну oracle-подборку. По умолчанию выходные токены
приложением не ограничены, thinking выключен, seed равен 42, temperature — 0.
Ограничение окна модели при этом сохраняется.

Только отдельная команда `run` выполняет генерацию. Она принимает подготовленный
`--prepared`, новый `--output` и явный `--endpoint` OpenAI-совместимого сервера.
Для закрытого SSH-туннеля допускается HTTP на loopback; для внешнего сервера
требуется HTTPS. Ключ берётся из `ORACLE_ABLATION_API_KEY` либо переменной,
указанной через `--api-key-env`. Перенаправления, proxy из окружения и повторные
HTTP-попытки отключены.

`--resume` разрешает пропустить только уже завершённые, совпадающие по хешам
ветки. Запись `started` после прерывания означает неизвестный исход запроса:
утилита не отправит его повторно автоматически. `finish_reason=length` надо
отметить как обрезанный результат, даже если HTTP-запрос успешно завершился.

## Подготовка исходных данных

1. Зафиксируйте полный отчёт с вопросами, выбранным контекстом, планами и
   манифестом источников. Для уточняющих вопросов сохраните исходный предмет
   диалога и ограничения пользователя.
2. Зафиксируйте снимок docstore и точный список разрешённых физических файлов.
   Для общего корпуса это экспорт `ready-global-only`, не все файлы docstore.
3. До получения новых ответов опишите обязательные факты, запрещённые выводы и
   допустимые оговорки. У каждого требования должен быть проверяемый источник.
4. Выберите исходные TextNode и при необходимости точные диапазоны символов.
   Диапазон обязан сохранять всё необходимое условие или определение, а не
   обрывать его после удобного слова. Текст не пересказывайте.
5. Проверьте хеши и лимит контекста. Превышение бюджета — ошибка подготовки,
   а не разрешение незаметно обрезать доказательства.

Полный раздел не всегда означает весь документ. Например, перечень должен быть
передан целиком, а формула — вместе с определениями и условиями применимости.
Отдельный выбор oracle используется только для диагностики. Он не должен становиться
таблицей маршрутизации запросов по известным названиям документов в продукте.

## Что обязательно записать

- SHA кода утилиты и модулей подготовки промпта;
- хеши отчёта, docstore, разрешённых источников и oracle-манифеста;
- идентификатор модели, наблюдаемую ревизию и идентичность runtime;
- источник сведений о ревизии: запись cache ref не равнозначна хешу всех
  загруженных весов;
- параметры запроса, флаг thinking и наличие ограничения выходных токенов;
- размер исходного контекста и полного промпта, хеш каждого запроса;
- первичный ответ, время, usage и finish reason;
- ошибки и незавершённые запросы без скрытого повторного запуска.

Одинаковый seed не гарантирует побитовую воспроизводимость на другом runtime.
При неоднозначном результате повторите пары; не выдавайте единичное улучшение
за устойчивый эффект. Изменившаяся модель, инструкция или разметка требует нового
эксперимента, а не дописывания старого отчёта.

## Как оценивать

Проверяйте ответ по рубрике, а не по числу ссылок и найденных документов:

- все ли обязательные факты и части вопроса раскрыты;
- верны ли определения, формулы, единицы и применимость;
- не заменено ли основное правило частным случаем;
- нет ли противоречия между начальным выводом и дальнейшим объяснением;
- не добавлены ли неподтверждённые расшифровки и выводы;
- соблюдены ли явные исключения пользователя.

Для каждого требования отмечайте `supported`, `missing`, `incorrect` или
`uncertain` с ориентиром в источнике и фрагментом проверяемого ответа.
Наличие настоящей ссылки само по себе не означает `supported`.

Итоговые `PASS`, `PARTIAL`, `FAIL` — смысловая оценка по заранее записанной рубрике.
Автоматическое совпадение слов не заменяет смысловую проверку. После изучения
ответов прежние heldout-вопросы считаются регрессиями; для независимой приёмки
нужны новые, не использованные при настройке вопросы.

Указывайте, кто выполнял разметку и проверку. Если это независимые ИИ-агенты, а
не предметный специалист, так и записывайте в отчёте. Проверяемые цитаты и скрытые
метки A/B полезны, но не превращают ИИ-оценку в человеческую приёмку и не устраняют
риск ошибочной рубрики.

## Как интерпретировать разницу

| Наблюдение | Что проверять следующим |
| --- | --- |
| Oracle верен, actual неверен | Отбор конкретных строк, полноту разделов, упаковку, порядок и шум контекста |
| Обе ветки неверны при достаточном oracle | Инструкции, интерпретацию, модель и проверку смысла |
| Обе ветки верны, старый итоговый ответ неверен | Дальнейшие стадии проверки, исправления и форматирования |
| Oracle хуже actual | Достаточность ручной подборки, потерянные условия, порядок, вариативность генерации |

Это диагностические направления, не автоматическое доказательство единственной
причины. Более короткий oracle одновременно меняет и полноту нужных сведений,
и количество шума. Чтобы различить эти факторы, нужен дополнительный вариант
«actual плюс недостающий исходный фрагмент» с той же политикой бюджета.

## Безопасность и границы

- Запускайте из канонического checkout на `dev`, сохраняя чужие изменения.
- Используйте последовательные запросы; не меняйте рабочую модель или GPU.
- Не создавайте тестовые данные в production-БД и не переиндексируйте корпус.
- Не включайте чужие проекты и чаты в общий oracle. Для проверки приватных
  областей нужен отдельный разрешённый снимок и манифест доступа.
- Передавайте секреты только через окружение или существующий защищённый канал.
- Сырые документы, вопросы и ответы сохраняйте в закрытых QA-артефактах, не в Git.
- Успешный эксперимент не отменяет браузерных проверок, проверки изоляции и
  независимой приёмки полного пользовательского пути.
