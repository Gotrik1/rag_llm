# ADR-0001: Безопасный общий кэш ответов RAG

## Статус

Accepted

## Контекст

Одинаковые вопросы по общим документам должны получать уже рассчитанный ответ
независимо от аккаунта пользователя. При этом документы проекта и чата
изолированы по владельцу, а Redis также обслуживает долговечные очереди задач.
Ранний кэш до retrieval не может доказать, на каких документах основан ответ:
его ключ зависел от проектного промпта и списка исключённых файлов, поэтому
общие ответы фрагментировались по пользователям, а приватные ответы создавали
высокую кардинальность ключей.

## Драйверы решения

- нельзя переиспользовать ответ, содержащий факты из чужого проекта или чата;
- общий ответ должен переиспользоваться между пользователями;
- изменение модели, промпта или выбранных доказательств должно менять ключ;
- кэш не должен вытеснять задания из очередей и не является источником истины;
- похожие формулировки могут иметь разный смысл в нормативных документах.

## Рассмотренные варианты

### Кэшировать ответ до retrieval по вопросу и пользовательской области

Быстро, но общий ответ фрагментируется по проектам. Корректность зависит от
идеальной инвалидизации всей области документов, а приватные запросы засоряют
кэш.

### Semantic cache по близости вопросов

Даёт больше попаданий, но может смешать разные ценовые категории, редакции,
исключения и формулы. Для нормативного RAG риск неверного фактического ответа
выше ожидаемой экономии.

### Retrieval-first exact cache только для общих доказательств

Перед чтением кэша система заново понимает запрос и выбирает документы. Кэш
разрешён только если каждый выбранный фрагмент однозначно относится к активному
общему документу и вопрос не зависит от предыдущей реплики.

## Решение

1. Удалить ранний кэш готового ответа до retrieval.
2. Разрешать exact cache генерации только после retrieval, когда все выбранные
   источники однозначно сопоставлены активным общим документам.
3. Для общего ответа использовать базовый системный промпт без имени проекта,
   памяти и истории чата. Ключ включает модель, полный базовый промпт, исходный
   вопрос, интерпретацию намерения и точный выбранный контекст.
4. Если выбран хотя бы один проектный/чатовый/неоднозначный источник либо
   retrieval-запрос дополнен историей, чтение и запись answer cache запрещены.
5. Сохранить свободу LLM только при нормализации намерения и построении
   поисковых запросов. Генерация ответа остаётся строго ограниченной найденными
   доказательствами и проверяемыми ссылками.
6. Вынести вытесняемый кэш в отдельный Redis с лимитом 256 MiB,
   allkeys-lru, без AOF и снимков. Долговечные очереди остаются в отдельном
   Redis с AOF и noeviction.
7. Сохранить TTL 7 суток и текущую очистку кэша при изменении корпуса, модели,
   промпта или режима обработки.

## Последствия

### Положительные

- один общий ответ доступен всем пользователям без межпроектной утечки;
- приватные ответы не создают ключи answer cache;
- точное содержимое доказательств фактически входит в версию ключа;
- переполнение кэша не блокирует очереди и автоматически лечится LRU;
- при отказе или очистке кэша система продолжает работать через обычную
  генерацию.

### Отрицательные

- retrieval и понимание запроса выполняются даже при попадании в answer cache;
- вопрос по общим документам не кэшируется, если retrieval примешал приватный
  фрагмент или имя источника неоднозначно;
- отдельный Redis добавляет один небольшой контейнер в эксплуатации.

### Риски и меры

- Ложная классификация источника: алиасы с глобальным и приватным владельцем
  считаются неоднозначными и отключают кэш.
- Устаревший ответ: ключ зависит от точного выбранного контекста, а операции
  изменения корпуса дополнительно очищают namespace.
- Рост кардинальности нормализации запросов: отдельный Redis ограничен памятью,
  TTL и LRU; эти записи не содержат готовых фактов из приватных документов.

## Не делаем

- не применяем semantic similarity для выдачи готового ответа;
- не кэшируем ответы по документам проекта и чата;
- не даём LLM права дополнять факты вне найденного контекста.
