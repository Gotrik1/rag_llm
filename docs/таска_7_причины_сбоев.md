# Возможные точки сбоя

## Сценарий: пользователь задаёт вопрос

### 1. React UI → `web_ui.py`

Возможные ошибки:

* недоступен backend;
* превышен таймаут запроса;
* передан пустой или некорректный вопрос;
* превышен допустимый размер запроса;
* пользователь не авторизован;
* отсутствует или недоступен выбранный проект/flow.

Результат: пользователь не получает ответ, UI должен показать сообщение об ошибке и возможность повторить запрос.

### 2. `web_ui.py` → `rag_agent.py`

Возможные ошибки:

* сервис `rag_agent.py` недоступен;
* передан неизвестный идентификатор flow;
* не найден контекст проекта;
* ошибка формирования параметров запроса;
* превышен внутренний таймаут.

Результат: backend возвращает контролируемую ошибку без раскрытия технических деталей.

### 3. Проверка кэша в Redis

Возможные ошибки:

* Redis недоступен;
* ошибка подключения или авторизации;
* повреждённая запись в кэше;
* запись существует, но имеет некорректный формат;
* истёк TTL;
* коллизия ключей между проектами или пользователями.

Результат: при недоступности Redis запрос должен продолжить обработку без кэша. Ошибка Redis не должна полностью блокировать получение ответа.

### 4. Поиск evidence в Qdrant и BM25

Возможные ошибки:

* Qdrant или BM25 недоступны;
* индекс ещё не создан;
* индекс не соответствует текущей версии документа;
* ошибка формирования embedding;
* пустой результат поиска;
* найдены нерелевантные фрагменты;
* превышен таймаут поиска;
* ошибка фильтрации по проекту, документу или правам доступа.

Результат: система возвращает предупреждение об отсутствии достаточных источников либо выполняет ограниченный fallback-сценарий.

### 5. Формирование контекста

Возможные ошибки:

* контекст превышает лимит модели;
* фрагменты дублируются;
* нарушен порядок разделов;
* потеряны метаданные источников;
* в контекст попали документы другого проекта;
* не удалось определить наиболее релевантные фрагменты.

Результат: контекст должен быть сокращён, дедуплицирован и проверен перед передачей в модель.

### 6. Запрос к Ollama или внешнему провайдеру

Возможные ошибки:

* Ollama или внешний провайдер недоступен;
* модель не загружена;
* неверно указано имя модели;
* превышен контекстный лимит;
* превышен таймаут генерации;
* внешний API вернул ошибку авторизации или лимита;
* модель вернула пустой ответ;
* ответ модели не соответствует ожидаемому формату;
* генерация была прервана.

Результат: система должна вернуть понятное сообщение об ошибке, сохранить техническую причину в логах и при наличии настроенного fallback попробовать резервную модель.

### 7. Формирование ответа и источников

Возможные ошибки:

* модель сослалась на источник, которого нет в отобранном контексте;
* не удалось сопоставить цитату с документом;
* отсутствуют метаданные документа;
* Markdown сформирован некорректно;
* JSON-ответ не соответствует контракту API;
* предупреждения или источники потерялись при сериализации.

Результат: перед отправкой ответ должен проходить валидацию структуры, источников и обязательных полей.

### 8. Сохранение ответа в Redis

Возможные ошибки:

* Redis недоступен;
* превышен допустимый размер записи;
* ошибка сериализации;
* некорректно установлен TTL;
* ответ сохранён под неправильным ключом.

Результат: ошибка сохранения в кэш не должна влиять на возврат уже сформированного ответа пользователю.

### 9. `web_ui.py` → React UI

Возможные ошибки:

* backend вернул ошибочный HTTP-статус;
* получен невалидный JSON;
* соединение разорвано до получения полного ответа;
* ответ превышает допустимый размер;
* UI не смог обработать отдельные поля ответа.

Результат: UI должен корректно показать ошибку или частичный результат, не ломая интерфейс чата.

### 10. Отображение ответа пользователю

Возможные ошибки:

* Markdown не отрендерился;
* формулы, таблицы или ссылки отображаются некорректно;
* источники не открываются;
* предупреждение об отсутствии evidence не показано;
* длинный ответ нарушает вёрстку;
* пользователь повторно отправил вопрос до завершения предыдущего запроса.

Результат: UI должен экранировать опасный контент, поддерживать длинные ответы и блокировать или явно разделять параллельные запросы.

## Сценарий: пользователь загружает документ

### 1. Выбор файла в React UI

Возможные ошибки:

* выбран неподдерживаемый формат;
* размер файла превышает лимит;
* файл пустой;
* файл повреждён;
* имя файла содержит недопустимые символы;
* пользователь не имеет прав на загрузку документа в проект;
* пользователь повторно загружает тот же файл.

Результат: основные проверки должны выполняться до отправки файла на backend.

### 2. React UI → `web_ui.py`

Возможные ошибки:

* backend недоступен;
* соединение прервано во время загрузки;
* превышен таймаут;
* multipart-запрос сформирован некорректно;
* файл загружен не полностью;
* отсутствует идентификатор проекта;
* превышена серверная квота.

Результат: незавершённая загрузка не должна создавать запись о документе или запускать индексацию.

### 3. Передача документа в сервис индексации

Возможные ошибки:

* сервис индексации недоступен;
* файл не найден во временном хранилище;
* ошибка передачи файла между сервисами;
* документ уже находится в обработке;
* задача индексации потеряна после перезапуска сервиса;
* не удалось определить тип документа.

Результат: задача должна иметь идентификатор и статус, позволяющий повторить обработку без повторной загрузки файла.

### 4. Извлечение текста

Возможные ошибки:

* формат документа не поддерживается;
* документ защищён паролем;
* текст отсутствует и документ состоит из изображений;
* некорректная кодировка;
* повреждена структура PDF, DOCX или другого файла;
* извлечён пустой текст;
* часть страниц не обработана;
* таблицы, формулы или списки извлечены некорректно.

Результат: документ не должен считаться успешно проиндексированным, если текст не был извлечён либо извлечён частично без предупреждения.

### 5. Разбиение текста на разделы и фрагменты

Возможные ошибки:

* документ разбит на слишком крупные фрагменты;
* документ разбит на слишком мелкие фрагменты;
* потеряны заголовки и структура разделов;
* один фрагмент превышает лимит embedding-модели;
* появились пустые или дублирующиеся фрагменты;
* потеряна связь фрагмента с исходным документом и страницей;
* нарушена последовательность фрагментов.

Результат: перед индексацией необходимо валидировать количество, размер и метаданные фрагментов.

### 6. Построение векторов

Возможные ошибки:

* embedding-модель недоступна;
* превышен лимит запросов;
* модель вернула вектор неправильной размерности;
* часть фрагментов не получила embedding;
* использована другая версия embedding-модели;
* превышен таймаут обработки;
* пакетная обработка завершилась частично.

Результат: нельзя смешивать в одном индексе векторы разных моделей или разной размерности без явной миграции.

### 7. Обновление Qdrant

Возможные ошибки:

* Qdrant недоступен;
* коллекция не существует;
* схема коллекции не соответствует размерности векторов;
* часть векторов записалась, часть — нет;
* произошёл конфликт идентификаторов;
* старые фрагменты документа не удалены;
* новые данные записаны в неправильный проект;
* недостаточно места на диске.

Результат: обновление документа должно быть идемпотентным и по возможности атомарным: либо новая версия полностью доступна, либо используется предыдущая.

### 8. Обновление BM25-индекса

Возможные ошибки:

* BM25-индекс недоступен;
* индекс заблокирован другой операцией;
* ошибка токенизации;
* использован неправильный язык или анализатор;
* новые фрагменты не добавлены;
* старые фрагменты не удалены;
* состояние BM25 не соответствует Qdrant.

Результат: Qdrant и BM25 должны обновляться согласованно. При частичном обновлении документ должен получать статус ошибки индексации.

### 9. Очистка кэша Redis

Возможные ошибки:

* Redis недоступен;
* очищены не все ответы, связанные с документом;
* очищен кэш других проектов;
* ключи невозможно связать с изменённым документом;
* очистка произошла до успешного завершения индексации.

Результат: кэш следует очищать только после успешного обновления поисковых индексов. При недоступности Redis индексация может завершиться, но система должна зафиксировать необходимость повторной очистки кэша.

### 10. Возврат результата индексации

Возможные ошибки:

* backend ожидает синхронный ответ, а индексация выполняется дольше HTTP-таймаута;
* сервис вернул количество созданных фрагментов, хотя часть записей не сохранилась;
* потерян статус обработки;
* UI получил невалидный ответ;
* пользователь не понимает, завершилась ли индексация.

Результат: для длительной обработки предпочтителен асинхронный сценарий со статусами:

```text
UPLOADED
PROCESSING
INDEXED
FAILED
```

### 11. Отображение результата пользователю

Возможные ошибки:

* показано неверное количество обработанных фрагментов;
* документ отображается как готовый до завершения индексации;
* ошибка индексации не показана;
* отсутствует возможность повторить обработку;
* пользователь отправляет вопрос по документу до завершения индексации.

Результат: до статуса `INDEXED` документ не должен участвовать в поиске либо должен явно отображаться как находящийся в обработке.

# Критичные сценарии частичного сбоя

Особенно необходимо обработать ситуации, когда операция выполнилась только частично:

1. Векторы записаны в Qdrant, но BM25 не обновлён.
2. BM25 обновлён, но векторы не записаны.
3. Индексы обновлены, но кэш Redis не очищен.
4. Файл принят, но задача индексации не запущена.
5. Индексация завершена, но UI получил таймаут и показывает ошибку.
6. Ответ модели сформирован, но не был передан пользователю.
7. Ответ возвращён пользователю, но не сохранён в кэш.
8. Новый документ проиндексирован, но старые фрагменты предыдущей версии остались в индексах.

Для таких случаев необходимы:

* единый идентификатор операции;
* явные статусы обработки;
* идемпотентный повтор операции;
* журналирование каждого этапа;
* очистка частично записанных данных;
* повторные попытки для временных ошибок;
* технические метрики и алерты;
* корреляционный идентификатор запроса во всех сервисах.
