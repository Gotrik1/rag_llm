# Каталог внешних систем

## 1. Ozon Seller API

**Описание**
API маркетплейса Ozon для управления товарами, заказами и другими сущностями магазина.

**Ответственность**
Команда интеграций / backend.

**SLA / доступ**
Зависит от доступности API Ozon.

### Лимиты

**Общие частотные ограничения:**

* До **50 RPS (requests per second)** на все методы с одного Client ID — лимит применяется глобально ко всем Seller API методам. ([dev.ozon.ru][1])
* Для некоторых методов может быть ограничение **не чаще 2 запросов в секунду** независимо от продавца. ([dev.ozon.ru][2])
* В документации также встречаются рекомендации не превышать **10 запросов в секунду по умолчанию** для большинства методов, если в описании не указано иначе. ([dev.ozon.ru][3])
* Ограничения могут отличаться для разных методов (см. официальные спецификации Ozon API).

**Ozon Performance API (рекламные отчёты):**

* До **100 000 запросов в сутки** по ключу Performance API. ([docs.ozon.ru][4])
  *(подробное описание таблиц вам уже есть — это реальная документация Ozon)*

### Типовые ошибки

* HTTP `429 Too Many Requests` — превышение лимита частоты/суточного лимита.
* Ошибки авторизации — неверный Client ID/API key.

**Owner / контакт**:

* Команда API/интеграций.

## 2. Wildberries API

**Описание API Wildberries**
Официальное API Wildberries используется для интеграции с маркетплейсом, включая работу с каталогом, заказами, остатками и другими функциями. Документация доступна на [dev.wildberries.ru](https://dev.wildberries.ru).

**Ответственность:** Команда интеграций / backend.

**SLA / доступ:** Доступность API зависит от состояния и доступности Wildberries.

**Лимиты:**
Wildberries предоставляет информацию о лимитах не только через официальную документацию, но и в **заголовках ответов API**. Эти данные включают информацию о том, сколько запросов осталось до исчерпания лимита, когда можно будет делать следующий запрос, и другие параметры, связанные с лимитами. Это очень важно, потому что позволяет точно планировать обращения к API и избежать ошибок из-за превышения лимита.

На данный момент мы не используем эти данные, но в будущем это потребует рефакторинга, чтобы учитывать эту информацию для эффективной работы с API и предотвращения ошибок из-за превышения лимитов.

Кроме того, **если API используется вне правил (например, при скрапинге или чрезмерных автоматических запросах), можно столкнуться с ошибкой 429 ("Too Many Requests")**.

Для получения точных данных о лимитах можно обратиться к официальной документации на [dev.wildberries.ru](https://dev.wildberries.ru).

### Типовые ошибки

* `429 Too Many Requests` (слишком частые запросы).
* Ошибки валидации API параметров.

**Owner / контакт:**

* Команда API/интеграций.

## 3. Google Sheets API

### Использование Google Web-API для работы с системой**

Мы предпочитаем не использовать REST API. Вместо этого мы активно применяем функциональность Google Web-API, разворачивая небольшие HTTP-сервера, предоставляемые Google, для доступа к системе.

Этот подход имеет несколько преимуществ:

1. **Отсутствие необходимости в создании отдельных Google-проектов**. Не нужно заниматься настройкой и управлением проектами в Google Cloud, что значительно упрощает процесс.

2. **Гибкость и масштабируемость**. Мы можем создавать множество аккаунтов без ограничений и легко запускать необходимые серверы. Это позволяет эффективно управлять доступом и быстро настраивать рабочие окружения.

3. **Упрощение работы с технической поддержкой**. Разворачиваемые HTTP-сервера позволяют организовать доступ в систему для различных пользователей (например, сотрудников технической поддержки) без дополнительных сложностей.

Таким образом, данный подход позволяет значительно упростить технические процессы и обеспечить бесперебойную работу.

### Ответственность

Data / BI команда.

**SLA / доступ**
Зависит от доступности сервисов Google Workspace.

### Лимиты

**Квоты использования (из официальной документации)**

* **Чтение: До 300 запросов в минуту на проект.** ([Google for Developers][5])
* **Чтение: До 60 запросов в минуту на пользователя в проекте.** ([Google for Developers][5])
* **Запись: До 300 запросов в минуту на проект.** ([Google for Developers][5])
* **Запись: До 60 запросов в минуту на пользователя в проекте.** ([Google for Developers][5])

> Превышение этих лимитов возвращает HTTP **429 Too Many Requests**. ([Google for Developers][5])

Дополнительно: нет строго ограниченного **суточного** количества запросов, но действуют **промежуточные квоты** сервисов Google. ([Google for Developers][5])

### Типовые ошибки

* `429 Too Many Requests` — превышение квот.
* `403` — отсутствие прав доступа для учетных данных.

**Owner / контакт**

* Data / BI команда.

## 4. Telegram Bot API

**Описание**
Телеграм-боты используют официальный **Telegram Bot API** для отправки/получения сообщений.

**Ответственность**
Team, поддерживающая ботов (backend).

**SLA / доступ**
Зависит от доступности Telegram API.

### Лимиты

Telegram Bot API имеет собственные ограничения, например:

* Сообщения/методы ограничиваются для предотвращения спама (детали в официальной документации). *(детальное количество в секунду зависит от метода)*

**Типовые ошибки**

* `429 Too Many Requests` — слишком частые обращения.
* `401 Unauthorized` — неверный токен.

**Owner / контакт**

* DevOps/Backend команда по ботам.

## 5. Платёжный провайдер (конкретная внешняя система)

**Описание**
Внешняя система обработки платежей (например, ЮMoney, банки, эквайринг и т.п.).
**Точный провайдер должен быть указан в контракте/документации проекта.**

**Ответственность**
Finance / backend.

**SLA / доступ**
Зависит от SLA выбранного провайдера (в контракте/договоре).

### Типовые ошибки

* `402 Payment Required` / транзакции отклонены.
* Временная недоступность сервера провайдера.

**Owner / контакт**

* Команда интеграций с платёжным провайдером.
