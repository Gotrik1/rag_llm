# Bounded Context Map

**Назначение:** Зафиксировать реальные границы логических контекстов системы и характер их взаимодействия.

> Bounded Context (ограниченный контекст) — это логическая граница внутри системы, внутри которой используется своя модель данных и своя терминология.

---

## 1. Реальные Bounded Context в 10X

На текущей архитектурной стадии система разделяется на три устойчивых контекста:

1. **Identity & Access (IAM)** — контекст управления доступом
2. **Marketplace Integration** — контекст интеграции с маркетплейсами
3. **Analytics Engine** — контекст управленческой аналитики и расчётов

> Остальные модули являются субдоменами внутри Analytics Engine.

---

## 2. Контекст 1 — Identity & Access (IAM)

### Граница

* Owner (владелец бизнеса)
* Workspace (граница одного бизнеса)
* RBAC (role-based access control — ролевая модель доступа)
* Роли и права

### Ответственность

* Изоляция данных по Workspace
* Управление доступами пользователей
* Определение границы владения бизнесом
* Контроль авторизации для других контекстов

IAM не занимается бизнес-логикой продаж или расчётов.

---

## 3. Контекст 2 — Marketplace Integration

### Граница

* Cabinet (подключённый кабинет продавца)
* API Credentials (ключи доступа к API)
* Sync Sessions (сессии синхронизации)
* Raw Marketplace Data (сырые данные маркетплейса)

### Ответственность

* Подключение маркетплейсов (WB / Ozon)
* Получение данных через API
* Нормализация данных во внутренний формат
* Изоляция внешней модели API от внутренней модели системы

Это инфраструктурный контекст.
Он не рассчитывает прибыль и не строит управленческую аналитику.

---

## 4. Контекст 3 — Analytics Engine

(ранее — Profit Engine)

### Граница

Включает:

* Catalog (SKU — товарная единица)
* Unit Economics (юнит-экономика)
* Operations (Orders / Buyouts — заказы и выкупы)
* RNP (оперативная отчётность)
* Financial Fact (фактический финансовый отчёт)
* Planning (планирование)
* External Costs (внешние расходы)
* Ads & Search Analytics (рекламная и поисковая аналитика)

### Ответственность

* Расчёт прибыли
* Управленческая аналитика
* Консолидация P&L (отчёт о прибылях и убытках)
* Прогнозирование
* Связка рекламы, продаж и финансов

Это домен бизнес-аналитики, а не просто "движок прибыли".

---

## 5. Взаимодействие контекстов

### 5.1 Identity → Marketplace Integration / Analytics Engine

Identity является **Upstream** (вышестоящим контекстом) для остальных.

> Upstream — контекст, модель которого используется другими контекстами.

Тип отношения: **Conformist**

> Conformist — подчинённый контекст принимает модель вышестоящего без изменения.

Marketplace Integration и Analytics Engine принимают модель Workspace и правила доступа IAM без модификации.

---

### 5.2 Marketplace Integration → Analytics Engine

Marketplace Integration поставляет данные:

* товары,
* заказы,
* финансы,
* рекламу.

Analytics Engine использует их для расчётов.

Тип отношения: **Customer–Supplier**

> Customer–Supplier — один контекст (Customer) определяет требования к данным, другой (Supplier) обязан поставлять данные в согласованном формате.

Analytics Engine задаёт требования к нормализованной модели данных.
Marketplace Integration реализует адаптацию API под эту модель.

---

## 6. Anti-Corruption Layer (ACL)

> Anti-Corruption Layer — слой трансляции, защищающий внутреннюю модель от прямого влияния внешних API.

ACL применяется между:

WB / Ozon API
→ Marketplace Integration

Внешние модели маркетплейсов не проникают напрямую в Analytics Engine.
Integration выполняет преобразование форматов и изоляцию изменений API.

---

## 7. Shared Kernel

> Shared Kernel — общая часть модели, используемая несколькими контекстами.

В текущей архитектуре Shared Kernel между контекстами отсутствует.

Важно:

* Термин SKU является сквозным бизнес-понятием.
* Однако его внутренняя модель и вычислительная логика принадлежат Analytics Engine.
* Другие контексты могут оперировать идентификатором SKU, но не управляют его бизнес-семантикой.

---

## 8. Архитектурная схема влияния

```markdown
Identity & Access
        ↓
Marketplace Integration
        ↓
Analytics Engine
```

Логика влияния:

1. IAM определяет границы доступа.
2. Integration получает и нормализует данные.
3. Analytics Engine рассчитывает показатели и строит отчётность.

---

## 9. Ключевой вывод

Система 10X состоит из трёх логических слоёв:

* Контекст изоляции бизнеса (Identity)
* Контекст интеграции данных (Marketplace Integration)
* Контекст управленческой аналитики (Analytics Engine)

Система строится вокруг модели бизнеса пользователя,
а не вокруг API маркетплейсов.

API — источник данных.
Workspace — граница бизнеса.
Analytics Engine — ядро управленческих расчётов.
