# Marketplace Integration Bounded Context

## Назначение

Marketplace Integration отвечает за подключение маркетплейсов и получение данных через их API.

Контекст обеспечивает:

* добавление кабинетов WB (Wildberries) и Ozon,
* хранение и защиту API-токенов,
* валидацию подключения,
* синхронизацию данных,
* адаптацию внешних API к внутренней модели.

Контекст не интерпретирует прибыль и не участвует в расчётах управленческой экономики.

---

## Граница контекста

Внутри контекста находятся:

* Cabinet (подключённый кабинет маркетплейса)
* Marketplace (тип платформы: WB / Ozon)
* API Credentials (ключи доступа)
* Sync Session (сессия синхронизации)
* Sync Status (статус синхронизации)
* Raw Marketplace Data (сырые данные маркетплейса)
* API Adapter (ACL — Anti-Corruption Layer, слой адаптации)

В контекст не входят:

* SKU как бизнес-единица
* UNIT (юнит-экономика)
* расчёт прибыли
* RNP (оперативная управленческая отчётность)
* P&L (отчёт о прибылях и убытках)
* планирование
* пользователи и роли

Контекст знает о принадлежности к Workspace, но не управляет доступами.

---

## Ubiquitous Language (Единый язык контекста)

Внутри контекста используется следующий язык:

* Cabinet — подключённый маркетплейс-кабинет
* Marketplace — тип платформы (WB / Ozon)
* API Token — ключ доступа
* Sync — процесс синхронизации данных
* Raw Data — данные в формате маркетплейса
* Adapter — слой трансляции API
* Validation — проверка валидности токена
* Integration Error — ошибка синхронизации

Этот язык не содержит терминов управленческой аналитики и расчёта прибыли.

---

## Core Responsibility (Ключевая ответственность)

Контекст отвечает за:

* подключение кабинета по токену,
* проверку валидности токена,
* периодическую или ручную синхронизацию,
* получение заказов, товаров, финансовых и рекламных данных,
* нормализацию данных к внутреннему формату,
* защиту чувствительных данных (API-токены).

Контекст не выполняет бизнес-расчёты и не принимает управленческие решения.

---

## Инварианты

* Cabinet принадлежит одному Workspace.
* Один Cabinet не может быть связан с несколькими Workspace.
* Сырые данные (Raw Data) не изменяются бизнес-логикой.
* Сырые данные хранятся отдельно от доменной аналитической модели.
* API-структуры маркетплейса не проникают напрямую в Analytics Engine.
* Ошибка синхронизации одного кабинета не влияет на другие кабинеты.

---

## Anti-Corruption Layer (ACL)

Между внешними API (WB / Ozon) и системой используется слой адаптации (ACL — Anti-Corruption Layer).

ACL обеспечивает:

* трансляцию моделей API во внутренний формат,
* изоляцию от изменений версии API,
* предотвращение утечки внешних структур во внутреннюю доменную модель.

Несмотря на наличие ACL, система остаётся зависимой от контрактов API маркетплейсов.

Analytics Engine не взаимодействует напрямую с API маркетплейса.

---

## Архитектурная роль

Marketplace Integration является инфраструктурным контекстом.

Он:

* поставляет данные,
* изолирует внешние системы,
* защищает токены,
* обеспечивает стабильность внутренней модели данных.

Контекст не содержит бизнес-логики прибыли и не участвует в формировании управленческой аналитики.
