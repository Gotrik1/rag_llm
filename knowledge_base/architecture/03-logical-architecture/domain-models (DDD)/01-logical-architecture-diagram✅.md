# 10X — Domain Model (Business-Oriented Version)

**Область:** Сквозная аналитика и управление прибылью на маркетплейсах

**Платформы:** Wildberries (WB), Ozon

**Статус:** Архитектурная версия для ревью

**RBAC:** В процессе разработки (учитывается как существующий в усечённом виде)

---

## 1. Domain Vision

**10X** — система управленческой аналитики маркетплейсов,
ориентированная на владельца бизнеса.

Система предназначена для:

* подключения кабинетов маркетплейсов,
* централизованного управления доступами,
* консолидации отчётности,
* расчёта управленческих метрик,
* анализа прибыльности бизнеса.

Основной субъект системы — **владелец бизнеса (Owner)**.

---

## 2. Domain Actors

### 2.1 Owner (Владелец бизнеса)

Главный субъект системы.

#### Полномочия

* создаёт Workspace,
* подключает кабинеты маркетплейсов (через API-токены),
* назначает администраторов,
* имеет полный доступ ко всей отчётности внутри своего Workspace.

Owner — юридический и логический владелец всех данных в рамках Workspace.

---

### 2.2 Workspace

Workspace — это изолированное пространство бизнеса.

#### Характеристики

* принадлежит одному Owner,
* содержит один или несколько кабинетов маркетплейсов,
* имеет собственную модель доступов (RBAC),
* хранит агрегированную управленческую отчётность.

Workspace — это граница бизнес-изоляции.

Разные бизнесы → разные Workspace → изоляция данных.

---

### 2.3 Administrator

Назначается Owner.

#### Полномочия

* управляет подключёнными кабинетами,
* управляет отчётностью,
* работает с данными внутри Workspace,
* не может удалить Owner,
* не может выйти за пределы Workspace.

---

### 2.4 Пользователи (в рамках RBAC)

RBAC находится в процессе разработки,
но модель предполагает следующие роли:

* Owner
* Admin
* (в будущем) Analyst / Viewer / Super Admin

На текущем этапе считаем, что:

> RBAC существует в базовом виде и ограничивает доступ на уровне Workspace.

---

## 3. Marketplace Integration Model

### 3.1 Cabinet (WB)

Wildberries

#### Определение

**WB Cabinet** — это подключённый в нашей системе API-доступ к конкретному кабинету продавца Wildberries.
Это не пользователь нашей системы, а внешний объект — бизнес-кабинет продавца на стороне WB, доступ к которому осуществляется через API-токен.

---

#### Создание

1. Пользователь Workspace добавляет **API-токен WB**.
2. Система выполняет:

   * проверку валидности токена,
   * проверку доступности API,
   * определение доступных разделов (scope),
3. При успешной валидации создаётся Cabinet и запускается первичная синхронизация.

---

#### Атрибуты

| Атрибут             | Описание                              |
| ------------------- | ------------------------------------- |
| Marketplace         | `Wildberries`                         |
| API Token           | Хранится в зашифрованном виде         |
| Token Status        | Valid / Expired / Revoked / Invalid   |
| Token Scopes        | Набор доступных API-разделов          |
| Connection Status   | Connected / Error / Not Synced        |
| Last Sync Timestamp | Дата последней успешной синхронизации |
| Sync Health         | OK / Partial / Failed                 |

---

#### Особенности WB

* Один бизнес-пользователь WB может иметь несколько кабинетов.
* Один токен WB может иметь **ограниченные права доступа (scope)**.
* Доступ к данным зависит от прав, выданных при генерации токена.
* При истечении или отзыве токена синхронизация прекращается.

---

#### Инварианты

* Кабинет принадлежит **ровно одному Workspace**.
* Один WB-кабинет не может быть привязан к нескольким Workspace.
* Без валидного токена синхронизация невозможна.
* Удаление кабинета в системе:

  * блокирует дальнейшую синхронизацию,
  * лишает Workspace доступа к отчётности,
  * не удаляет данные на стороне WB.

---

### 3.2 Cabinet (Ozon)

Ozon

#### Определение

**Ozon Cabinet** — это подключённый через API доступ к кабинету продавца Ozon внутри нашей системы.

Аналогично WB — это не пользователь нашей системы, а внешний бизнес-аккаунт продавца.

---

#### Создание

1. Добавление Ozon API credentials:

   * Client ID
   * API Key
2. Валидация через тестовый API-запрос.
3. При успехе — регистрация Cabinet и первичная загрузка данных.

---

#### Атрибуты

| Атрибут             | Описание                              |
| ------------------- | ------------------------------------- |
| Marketplace         | `Ozon`                                |
| Client ID           | Идентификатор клиента                 |
| API Key             | Ключ доступа                          |
| Credential Status   | Valid / Invalid / Revoked             |
| Connection Status   | Connected / Error                     |
| Last Sync Timestamp | Дата последней успешной синхронизации |
| Sync Health         | OK / Partial / Failed                 |

---

### Особенности Ozon

* Доступ предоставляется через пару ключей (Client ID + API Key).
* Права доступа определяются настройками кабинета Ozon.
* Возможна сегментация по складам / контрактам (зависит от конфигурации продавца).
* Нет гибкой granular-RBAC на уровне токена как у WB, права задаются на уровне ключа.

---

#### Инварианты

* Кабинет принадлежит одному Workspace.
* Один Ozon-кабинет не может быть подключён к нескольким Workspace.
* При невалидных credentials синхронизация невозможна.
* Удаление кабинета:

  * прекращает синхронизацию,
  * закрывает доступ к отчётности внутри системы,
  * не влияет на аккаунт продавца в Ozon.

---

### 3.3 Архитектурное уточнение

Важно зафиксировать:

* **Cabinet — это агрегат нашей доменной модели**, представляющий внешний Marketplace Account.
* Marketplace является дискриминатором типа кабинета (`WB | Ozon`).
* Поведение синхронизации реализуется через Marketplace-specific Adapter.
* Статус подключения — это не “статус пользователя”, а состояние валидности API-доступа.

## 4. Data Domains внутри Cabinet

Каждый кабинет содержит набор управленческих доменов отчётности.

Важно:
это **не независимые bounded contexts**,
а логические области аналитики внутри одного бизнеса.

---

### 4.1 Reference Domain (Справочные данные)

Назначение:

* хранение идентификаторов товаров,
* сопоставление SKU / offer_id / nmID,
* базовые товарные атрибуты.

Источник:

* API маркетплейса.

Инварианты:

* SKU уникален внутри кабинета.
* Без SKU расчёты невозможны.

---

### 4.2 UNIT Economics

Экономика единицы товара.

Содержит:

* себестоимость,
* комиссию,
* логистику,
* соинвест (Ozon),
* ручные корректировки.

Инварианты:

* UNIT фиксируется по дате.
* История переписывается.
* UNIT — база для управленческих расчётов.

---

### 4.3 RNP (Оперативная управленческая отчётность)

RNP — отчёт по прибыльности и ключевым метрикам.

Содержит:

* выручку,
* маржу,
* ДРР,
* КРРР,
* заказы,
* динамику.

Инварианты:

* RNP строится на заказах и выкупах.
* % выкупа моделируется внутри системы.
* Метрики могут уточняться до финализации статусов.
* RNP фиксируется по дате истории.

Дополнительно:

Система рассчитывает показатели в двух разрезах:

1. Base Economics (без соинвеста)
2. Actual Economics (с учётом соинвеста)

Инварианты:

* Соинвест не изменяет себестоимость.
* Соинвест влияет на конечную цену реализации.
* Метрики должны быть сопоставимы между режимами.

---

### 4.4 Financial Fact

**Financial Fact** — фактическая финансовая реализация продаж на маркетплейсе, получаемая из официальных отчётов площадки (например, еженедельных/месячных отчётов Wildberries или отчётов Ozon о реализации товара).

**Источник данных:**

* официальные **финансовые отчёты маркетплейса** (settlement/settlement reports) — документы, в которых маркетплейс показывает суммы продаж, удержанные комиссии, логистику, компенсации, возвраты и итоговые суммы к перечислению продавцу.

**Инварианты:**

* Financial Fact отражает **фактические расчёты маркетплейса**, а не прогнозные или промежуточные операционные данные.
* Данные Financial Fact обычно **запаздывают** по отношению к оперативной аналитике (например, расчёты заказов/выкупов).
* Financial Fact может **отличаться от оперативной управленческой отчётности** по причинам удержаний, корректировок, возвратов и особенностей расчёта маркетплейса.
* Financial Fact используется для **финансовой сверки и формирования P&L** (финансового результата) по бизнесу.

---

### 4.5 External Costs

Внешние расходы.

Содержит:

* внешнюю рекламу,
* блогеров,
* раздачи,
* офлайн-затраты.

Источник:

* ручной ввод пользователя.

Инвариант:

* Вносятся только пользователем.

---

### 4.6 Planning (Планирование)

Планирование — это набор целевых и прогнозных показателей, которые помогают оценить ожидаемые результаты продаж и финансового состояния бизнеса на маркетплейсах.

**Содержит:**

* планы продаж,
* планы маржи,
* сезонные прогнозы,
* прогнозы выручки и ключевых показателей.

**Инварианты:**

* **План ≠ факт** — значения, заданные в планах, не являются данными о реально совершённых продажах или уже перечисленных суммах.
* Плановые показатели задаются пользователем на основе анализа исторических данных, сезонности, трендов и собственных стратегических целей.
* План помогает определить целевые уровни продаж и прибыли, а также служит основой для сравнения с фактическими результатами и анализа отклонений.

**Дополнительно:**

* Аналитика планирования обычно включает оценку спроса и сезонных колебаний, что позволяет спрогнозировать, какие товары и в каких объёмах стоит завозить или активировать маркетинговые усилия.
* План сезонных продаж рассматривается как часть инструментов аналитики, а не как оперативные данные — он используется для оценки привлекательности инвестиций в ассортимент и определения будущих целевых показателей.

---

Да, в диалоге Дмитрий как раз акцентировал важную мысль:
**ценность системы в том, что она объединяет данные и даёт картину, которой нет у самих маркетплейсов.**

Маркетплейсы дают:

* разрозненные отчёты,
* рекламную статистику отдельно,
* продажи отдельно,
* финансы отдельно,
* без учёта вашей юнит-экономики.

А система:

* сводит всё в одной модели,
* связывает рекламу с заказами и выкупами,
* учитывает себестоимость,
* считает реальную прибыль,
* позволяет видеть влияние рекламных расходов на маржинальность.

### 4.7 Search & Ads Analytics (Поиск и рекламная аналитика)

Аналитика рекламы и поискового трафика с привязкой к финансовому результату.

**Источник:**

* рекламные API маркетплейсов,
* данные по показам, кликам, ставкам, расходам,
* данные по заказам и выкупам.

**Инварианты:**

* Данные маркетплейсов неполные по определению (алгоритмы ранжирования и аукциона не раскрываются).
* Рекламная статистика маркетплейсов не связана с реальной юнит-экономикой продавца.
* Система объединяет рекламу, продажи и финансы в единую модель.

**Ключевая ценность:**

* Видно влияние рекламных расходов на:

  * заказы,
  * выкупы,
  * маржу,
  * прибыль.
* Можно анализировать эффективность не только по кликам и конверсии,
  а по фактической прибыльности.
* Вся аналитика доступна в одном интерфейсе.

## 5. Business-Level Aggregation (Агрегация на уровне бизнеса)

На уровне Workspace (рабочее пространство бизнеса) система агрегирует данные:

* по кабинетам,
* по маркетплейсам,
* по SKU (товарным единицам),
* по периодам.

Формируется:

* консолидированный P&L (отчёт о прибылях и убытках),
* общая прибыль бизнеса,
* агрегированная аналитика по всем подключённым кабинетам.

> Кросс-платформенная аналитика (совместный анализ WB и Ozon) — возможна архитектурно, но может быть ограничена текущей моделью данных и бизнес-приоритетами — сейчас не применяется.

---

## 6. System-Wide Invariants (Системные инварианты)

1. Данные из разных Workspace изолированы.
2. Owner (владелец) — верхний уровень доступа.
3. Кабинет принадлежит только одному Workspace.
4. UNIT (юнит-экономика) — основа управленческих расчётов.
5. Факт и прогноз разделены.
6. История UNIT не переписывается.
7. RNP (оперативная отчётность) работает с заказами и выкупами.
8. Показатели рассчитываются в двух разрезах:
   — Base (без соинвеста),
   — Actual (с учётом соинвеста).

---

## 7. Уровни системы (иерархия)

```markdown
Owner (владелец бизнеса)
   ↓
Workspace (граница бизнеса)
   ↓
Marketplace Domain (домен маркетплейса: WB / Ozon)
   ↓
Cabinet (конкретный кабинет продавца)
   ↓
Data Domains (домены данных: заказы, финансы, реклама и др.)
   ↓
Reports & Analytics (отчёты и аналитика)
```

Иерархия строится от владельца бизнеса к источникам данных и далее к аналитике.

---

## 8. Ключевой принцип архитектуры

Система строится не вокруг API маркетплейсов,
а вокруг владельца бизнеса.

* API — источник данных.
* Marketplace — внешний контур.
* Workspace — граница одного бизнеса.
* Owner — центр управления и принятия решений.

Система выступает как связующее звено между бизнесом и маркетплейсами, объединяя разрозненные данные в управленческую модель.
