**Дата:** 2026-02-12

## Контекст

### 1. Ролевая модель

В системе существует **две роли** с четким разделением привилегий:

| Роль      | Описание                                      | Права                                                                                                                                                                         |
|-----------|-----------------------------------------------|-------------------------------------------------------------------------------------------------------------------------------------------------------------------------------|
| **Овнер** | Главная роль, полный доступ ко всем кабинетам | • Создание и управление кабинетами<br>• Добавление и управление администраторами<br>• Назначение доступов на уровне кабинетов<br>• Полный доступ ко всем данным и функционалу |
| **Админ** | Ограниченный доступ, назначается овнером      | • Доступ только к назначенным кабинетам<br>• Доступ только к разрешенным функциям<br>• **Нет прав** на изменение ролей<br>• **Нет прав** на управление доступами системы      |

**Роли без доступа:** не предусмотрены.

---

### 2. Реализация механизмов контроля доступа

#### 2.1. Локализация проверок

Проверки прав доступа **распределены по кодовой базе** и реализуются:

- В хендлерах запросов;
- В сервисных методах;
- В утилитах работы с ресурсами.

#### 2.2. Типовой паттерн реализации

```javascript
async spreadsheetSetGeneralPermissions({ spreadsheet_id, access_type, permission_type }) {
  if (!spreadsheet_id) throw Error("spreadsheet_id is required");
  if (!access_type) throw Error("access_type is required");
  if (!permission_type) throw Error("permission_type is required");

  const action = "spreadsheets/sharing/set";
  return this._handleResult(await this._fetch({
    action,
    ssId: spreadsheet_id,
    accessType: access_type,
    permissionType: permission_type
  }), action);
}
```

**Характеристики текущей реализации:**

- Проверки прав **встроены в бизнес-логику** методов;
- Отсутствует единый entry point для авторизации;
- Нет централизованного описания матрицы доступа;
- Код проверок **дублируется** для разных типов ресурсов.

#### 2.3. Обработка ошибок доступа

| Код                           | Условие возникновения            | Пример                             |
|-------------------------------|----------------------------------|------------------------------------|
| **401 Unauthorized**          | Пользователь не аутентифицирован | Запрос без токена                  |
| **403 Forbidden**             | Недостаточно прав для операции   | Админ пытается изменить роль       |
| **404 Not Found**             | Ресурс не существует             | Запрос несуществующего кабинета    |
| **500 Internal Server Error** | Серверная ошибка                 | Сбой БД, необработанное исключение |

### 3. Проблемы текущей реализации

#### 3.1. Архитектурные дефициты

❌ **Отсутствует единая матрица доступа**  
Права ролей нигде не зафиксированы явно — восстанавливаются только через анализ кода.

❌ **Дублирование логики проверок**  
Одна и та же проверка может быть реализована в нескольких местах с незначительными вариациями.

❌ **Риск пропуска проверок**  
Нет гарантии, что разработчик добавит проверку прав в новый эндпоинт — полагаемся на code review.

❌ **Низкая тестируемость**  
Логика авторизации не изолирована, сложно писать модульные тесты.

❌ **Сложность аудита**  
Невозможно получить актуальную матрицу доступа без ручного анализа всей кодовой базы.

#### 3.2. Операционные проблемы

- Каждый новый эндпоинт требует **индивидуальной реализации** проверок;
- Изменение прав роли требует **поиска и правки** всех мест использования;
- Онбординг новых разработчиков замедлен из-за непрозрачности системы прав;
- Compliance-проверки требуют **значительных трудозатрат**.

---

### 4. Предпосылки к изменению

Текущая реализация:

- Была достаточной на этапе **MVP** (2 роли, <20 эндпоинтов);
- Перестала удовлетворять потребностям при **масштабировании функциональности**;
- Создает **технический долг** при каждом добавлении новой операции;
- Не соответствует стандартам безопасности для **production-систем**.

---

### 5. Диагностика

**Критичность:** Высокая  
**Тренд:** Ухудшается с каждым новым эндпоинтом  
**Влияние на разработку:** Замедление +10–15% на каждую новую фичу  
**Влияние на безопасность:** Потенциальные уязвимости из-за пропущенных проверок
